# 游戏资源拓扑与数据引用模型

> **回答的问题**：整个游戏是怎么组织的？谁引用谁？武器/怪物/关卡/道具/过场动画/场景
> 这些业务数据是怎么互相调用的？
>
> **证据等级**：结构结论来自全量数据普查（GER 91,179 资源 / GE2RB 151,369 资源）；
> 引擎机制部分来自 `GER.exe` 反汇编（见 `reference-chain.md`）。

---

## 1. 先纠正一个前提：「套娃」不成立

最初的直觉是"system.res 是唯一入口，其余包是层层嵌套的树"。**实测推翻了这个模型。**

### 1.1 实测数据（GER）

| 指标 | v1（只走 ref_path） | v2（ref_path + names[3]） |
|---|---|---|
| 可达 PRES 节点 | 7,370 | **11,005** |
| 引用边 | 160,442 | **208,954** |
| **fan-in > 1 的节点** | 6,724 | **10,459** |
| 入口不可达的 PRES | 28,040 | ~24,400 |

### 1.2 三个结论

**① 它不是树，而是高度共享的 DAG。**

7,370 个节点里 **6,724 个（91%）被多个父节点引用**。最极端的：

| 资源 | 被引用次数 |
|---|---|
| `effect/Enemy/Share/PartDestruct/ps4/fromtga/PartDestruct_02.gnf.blz` | **3,264** |
| `g999_Base/model/field/Model/ps4/fromtga/Terminal_02.gnf.blz` | 3,241 |
| `g999_Base/model/field/Model/ps4/fromtga/Terminal_01.gnf.blz` | 2,778 |
| `g999_Base/model/field/Model/ps4/fromtga/Wall_11.gnf.blz` | 2,176 |

> **含义**：同一个贴图/模型被成百上千个 PRES 共享。这是资源复用的核心机制，
> 也意味着"从入口往下走"会不断遇到已访问节点 —— **必须去重，否则指数爆炸**。

**② `system.res` 不是唯一入口。**

有 **约 24,400 个 PRES 从入口完全不可达**。它们按需求加载：

| 目录 | 数量 | 加载方式 |
|---|---|---|
| `GameData/game/sound` | 11,856 | 音效，按事件触发 |
| `GameData/player/Male` | 5,391 | 角色外观，按装备组合 |
| `GameData/player/Female` | 5,387 | 同上 |
| `GameData/g999_Base/script` | 3,441 | 场景脚本，按关卡加载 |
| `GameData/player/Weapon` | 1,771 | 武器模型，按持有武器 |

**③ 深度只有 0–6 层。**

| depth | 节点数 |
|---|---|
| 0 | 1（system.res） |
| 1 | 3 |
| 2 | 1,034 |
| 3 | 925 |
| 4 | 3,053 |
| 5 | 5,979 |
| 6 | 10 |

非常扁平 —— 不是深递归，而是**宽共享**。

### 1.3 两条独立的引用通道

PRES 内部有**两个**指向其它 PRES 的通道，遍历时必须同时走：

| 通道 | 位置 | 边数（GER） |
|---|---|---|
| `ref_path` | 类型 B 条目的 `dataAt` 处字符串 | 160,449 |
| `names[3]` | 名字槽的第 4 项（完整路径） | 48,505 |

> 我最初只走了 `ref_path`，漏掉 3,635 个可达节点。这个错误靠"孤立 PRES 与
> `names[3]` 的交集"才发现。

## 2. 三类引用机制（必须分开理解）

| 机制 | 载体 | 解析方式 | 跨文件 | 规模 |
|---|---|---|---|---|
| **路径引用** | PRES 的 B 条目字符串 / `names[3]` | CRC64(路径) → qpck TOC | ✅ | 20 万条边 |
| **ID 引用** | tr2 表里的 `*_id` 字段 | 整数 ID → 另一张表的记录 | ✅（表间） | 数千个字段 |
| **URID** | 运行时 32 位整数 | label/sect/index | ✅ | **不落盘** |

> **关键**：URID 只存在于内存（已由随机基线实验证否其落盘，
> 见 `reference-chain.md` §6.1）。所以**能落盘重建的引用只有前两种**。

---

## 3. 业务数据放在哪里 —— 这是"散开"的真相

**核心发现：定义（数据表）与资源（美术文件）分居不同格式。**

| 业务 | 数据定义在哪 | 美术资源在哪 |
|---|---|---|
| **怪物** | `mission/*/db/enemy/Tr2/*.tr2`（每关 8 张表） | `effect/Enemy/**`、`enemy/model/**` |
| **关卡/任务** | `mission/*/db/**/*.tr2`、`layout/*.lob` | `field/**`、`mission/*/model/**` |
| **道具/装备** | `g999_Base/db/article/Tr2/*.tr2` | `player/Weapon/**` |
| **子弹** | `g999_Base/db/bullet/Tr2/*.tr2` | — |
| **角色外观** | `g999_Base/db/avatar/Tr2/*.tr2` | `player/{Male,Female}/**` |
| **文本** | `Locale/exported/*/`（每语言一份） | — |

### 3.1 数据库目录结构

```
data/GameData/
├─ g999_Base/db/          ← 全局数据库
│   ├─ article/Tr2/       道具、装备合成、商店
│   ├─ avatar/Tr2/        角色外观部件
│   ├─ bullet/Tr2/        子弹、Oracle Cell
│   ├─ enemy/Tr2/         怪物基础数据
│   ├─ npc/Tr2/           NPC
│   ├─ skill/Tr2/         技能
│   ├─ story/Tr2/         剧情
│   └─ ...
├─ mission/               ← 每关一个目录
│   ├─ 016_Training_NormalRank01/
│   │   ├─ db/enemy/Tr2/    ← 该关的 8 张怪物表
│   │   ├─ layout/          ← UI 布局 (.lob)
│   │   └─ model/           ← 该关专属模型
│   └─ ...
└─ Locale/exported/{de,en,es,fr,it,ru}/   ← 6 语言文本副本
```

### 3.2 tr2 表的字段证明"用 ID 互连"

对 6,407 个非 Locale 的 tr2 表做字段名普查，发现 **322 个不同字段名**。
其中 per-mission 怪物表的字段直接暴露了跨表引用：

| 字段名 | 指向 | 出现次数 |
|---|---|---|
| `en_mat_article_id` | **道具**（article） | 530 |
| `en_oracle_bullet_id` | **子弹**（bullet） | 530 |
| `en_hit_attack_id` | **攻击定义表** | 530 |
| `en_hit_defence_id` | **防御定义表** | 530 |
| `en_group_enemy_class_id` | **怪物类别** | 530 |
| `en_group_fam_id_array` | **怪物家族** | 530 |
| `virtual_motion_data_id_array` | **动作数据** | 530 |
| `en_atk_name` / `en_def_name` | 名称（不是路径） | 各 530 |

> **决定性结论：表与表之间用整数 ID 连接，不是路径字符串。**
>
> 这就是为什么你觉得"TR2、KST 都是散开的" —— 它们的连接靠 ID，
> 而 ID 的命名空间要**逐表建立**才能连起来，不能像 PRES 那样靠路径直接跳。

## 4. 完整引用图（概念模型）

```
qpck 归档
│   平铺: CRC64(路径) → 字节块
│
└─ PRES（语义层，11,005 个可达节点，DAG）
    │
    ├─[通道1] ref_path 字符串 ──CRC64──> qpck ──> 叶子资源
    ├─[通道2] names[3] 路径 ────CRC64──> qpck ──> 叶子资源
    │
    └─ 叶子资源
        │
        ├─ tr2  ◄── 数据表（业务定义）
        │    │  内部: Record / Field / Cell
        │    │  跨表: 用 *_id 字段指向另一张表
        │    │
        │    └─[ID]──> 另一张 tr2 表
        │         └─[ID]──> kst1 / tbl / …
        │
        ├─ kst1 ◄── 键值数据库
        │    │  内部: header / 位图索引 / Record
        │    └─[key]──> 同库内的记录
        │
        ├─ rtbl ◄── 引用表（0x200 字节一槽）
        │    └─ 槽内存路径字符串 ──CRC64──> qpck
        │
        ├─ tbl  ◄── 纯 u32 数组（无内部结构）
        │
        ├─ blz4 ◄── 压缩包装（解开是上述任一格式）
        │
        └─ 美术资源：gnf(贴图) / ixo(模型) / ssq(场景) / is14(音频)
```

### 4.1 为什么"武器怎么调用"很难回答

以武器为例，它的完整链路是**跨格式**的：

```
关卡/菜单 UI
   │  (硬编码路径，代码里)
   ▼
武器相关的 tr2 表（g999_Base/db/article/Tr2/equipment_*）
   │  字段: *_id，指向道具 ID
   ▼
道具表（article_*）→ 得到武器参数（攻击力/属性）
   │  另一个字段（如模型 ID 或路径）
   ▼
美术资源（player/Weapon/**）  ← 这部分是路径，能 CRC64 命中 qpck
```

**中间那几层是 ID，不是路径** —— 所以不能像 PRES 那样顺着字符串走下来。
必须先建立"某张表的 ID → 记录"的映射，才能继续。

## 5. 如何让人"一眼看出"拓扑 —— 可行方案

基于以上发现，建立可读拓扑需要**分三层做**：

### 第 1 层：PRES 资源图（已可做）

- 输入：入口 PRES
- 输出：DAG，节点 = PRES/资源，边 = ref_path / names[3]
- 难点：节点上万、边 20 万 —— 必须聚合成"目录级"才可读
- **建议**：按目录聚合成 ~50 个超节点，画有向图

### 第 2 层：tr2 表间 ID 关系图（需逐表建模）

- 输入：所有 tr2 表
- 方法：解析每张表的 Field 定义，识别 `*_id` 字段，
  再找出该 ID 对应哪张表（靠字段名前缀推断：`en_` → enemy 表，`art_` → article 表，`bb_` → bullet 表）
- 输出：表级关系图
- **这是最有价值但最费工的一层**

### 第 3 层：业务实体图（武器/怪物/关卡）

- 输入：第 2 层的表关系
- 方法：以"实体"为单位（一件武器 = 一行记录 + 它的 ID 引用闭包）
- 输出：某个武器引用了哪些表、哪些美术资源

## 6. 已验证 / 未验证

### 已验证 ✅

| 断言 | 规模 |
|---|---|
| PRES 是 DAG 而非树（91% 节点 fan-in > 1） | 7,370 节点全量 |
| 存在约 24,400 个入口不可达的 PRES | 全量 |
| 两条引用通道（ref_path / names[3]） | 全量，边数 160k / 48k |
| 深度 ≤ 6 | 全量 |
| tr2 表用 `*_id` 字段跨表引用 | 322 个字段名普查 |
| 业务数据按 `db/{域}/Tr2/` 分目录 | 6,407 张表 |
| 美术资源与数据表分居不同目录 | 全量路径分类 |

### 未验证 ⚠️

| 断言 | 现状 |
|---|---|
| `*_id` 的具体命名空间如何映射到表 | 只有前缀规律，未建立完整映射表 |
| 同名字段（如 `en_mat_article_id`）指向的是哪张表的哪个 ID | 未交叉验证 |
| `layout/*.lob` 的格式 | 完全未知 |
| `gmvl`（关卡几何）、`ssq`（场景）、`sco` 等格式 | 未解析 |
| 24,400 个孤立 PRES 的触发条件 | 只知按需，不知触发源 |
| tr2 的 `RecordMode` / `Asm` 语义 | 未解 |

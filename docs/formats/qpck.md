## 1. 概述

qpck 是 God Eater（God Eater RESURRECTION 与 God Eater 2 Rage Burst 共用）在 PC 上使用的
**资源归档容器**。游戏本体把绝大多数资源塞进若干个 `.qpck` 文件里，而非散落在目录中。

理解这个格式的意义在于：**它是 mod 的入口**。因为引擎支持多个归档之间的覆盖
（见 §5），只要能生成正确的 qpck，就能替换游戏里的任何资源。

### 1.1 一个反直觉的事实：qpck 不存文件名

qpck 的目录表只记录一个 64 位哈希，**不存储原始路径字符串**。这个哈希是资源路径
经过归一化后算出的 CRC64（见 `src/gecv/crc64.py`）。

这条事实有两个直接后果，请务必理解：

| 后果 | 说明 |
|---|---|
| 解包后文件名会丢失 | 若不知道路径→哈希的映射，解包出来的文件只能按哈希命名 |
| **打包必须知道真实路径** | 否则算出的哈希与游戏请求的哈希不一致，游戏会找不到资源，且**没有任何报错** |

> ⚠️ 这是本项目当前最大的未知项：我们还没有拿到权威的"路径→哈希"名字表。
> `_unnamed/` 目录就是这个问题的产物。名字表的来源见 §7。

## 2. 文件布局

```
偏移 0                     偏移 8                        偏移 8+count*20
+--------+--------+       +--------+--------+--------+   +------------------+
| magic  | count  |------>| TOC[0] | TOC[1] |  ...   |-->| 数据块 0         |
|  u32   |  i32   |       |  20B   |  20B   |        |   | 数据块 1         |
+--------+--------+       +--------+--------+--------+   | ...              |
   8 字节                    每条 20 字节，共 count 条    +------------------+
                                                              EOF
```

### 2.1 文件头（8 字节）

| 偏移 | 类型 | 字段 | 值 / 说明 |
|---|---|---|---|
| 0x00 | u32 LE | `magic` | 恒为 `0x37402858` |
| 0x04 | i32 LE | `count` | TOC 条目数 |

> `count` 用的是**有符号** 32 位整数（对应 C# 的 `ReadInt32`）。正常数据不会超过
> `2^31-1`，但解析时应当保持有符号以与原实现一致。

### 2.2 目录表 TOC（每条 20 字节）

`count` 条记录，从第 8 字节开始连续存放：

| 相对偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| +0x00 | i64 LE | `offset` | 该条目数据块在整个文件中的**绝对**偏移 |
| +0x08 | u64 LE | `hash` | 资源路径的 CRC64，是这条记录的**键** |
| +0x10 | i32 LE | `length` | 数据块长度（字节） |

### 2.3 数据区

紧跟 TOC 之后，**没有任何对齐填充**。每个数据块按 TOC 中的顺序首尾相接存放。

## 3. 样本中观察到的规律（非格式强制）

以下 5 条在 4 个真实样本上都成立，但严格来说是"我们观察到的样本规律"，
**不是**格式规范强制要求的。之所以校验它们，是为了能尽早发现理解偏差：

| # | 规律 | 违反时的含义 |
|---|---|---|
| 1 | 首个数据块偏移 `== 8 + count*20` | TOC 与数据区之间有未知内容 |
| 2 | 数据块严格首尾相接 | 存在空洞或重叠，我们的布局理解有误 |
| 3 | 末块末尾 `== 文件大小` | 文件尾部有未解释的字节（可能是签名/附加数据） |
| 4 | TOC 按 `hash` **升序**排列 | 暗示引擎用二分查找而非线性扫描（**未证实**，见 §6） |
| 5 | `hash` 不重复 | 单个文件内重复本应被去重；重复说明我们的去重规则理解有误 |

我们的解包器**默认严格校验** 1–3（违反则抛异常），4–5 只记录不报错。

## 4. 哈希算法：CRC64

详见 [`src/gecv/crc64.py`](../../src/gecv/crc64.py) 的模块文档。参数摘要：

| 参数 | 值 |
|---|---|
| 多项式 | `0x95AC9329AC4BC9B5` |
| 初始值 | `0xFFFFFFFFFFFFFFFF` |
| 结果异或 | `0` |
| 反射 | 是 | 
| 编码 | ASCII |

### 4.1 路径归一化（三条规则，缺一不可）

```
1. 反斜杠 → 正斜杠：     a\b      → a/b
2. 去掉前导斜杠：        /a/b     → a/b
3. 转大写：              a/B.res  → A/B.RES
```

**为什么大小写不敏感很重要**：这说明引擎把路径当作**标识符**处理，而不是当作
真实文件系统里的精确字节串。因此在 Windows 上 `Foo.res` 和 `foo.res` 会碰撞到同一个条目。

**为什么必须是 ASCII**：引擎用 ASCII 编码参与哈希。我们的实现特意使用了
`.encode("ascii")` 而非 `.encode()`（后者默认 UTF-8），遇到非 ASCII 字符会直接
抛出 `UnicodeEncodeError`——这是**有意为之**：与其猜引擎的真实行为并悄悄产生错误
哈希，不如明确失败。

## 5. 多重归档：mod 的运作基础

引擎按固定顺序加载多个归档。若同一个哈希在多个归档中都存在，**保留最先出现
的那个，忽略后来的**（先入为主）。

加载顺序：

```
1. bin_patch.qpck     ← 最优先，mod 放这里
2. bin.qpck
3. conf.qpck
4. data.qpck
```

这意味着：把修改后的资源打进 `bin_patch.qpck`，就能覆盖 `bin.qpck` 里的原版资源，
**无需改动任何原始游戏文件**。这是可逆、低风险的 mod 方式。

代码里的对应实现是 `MultiArchive` 类：

```python
ma = MultiArchive([r"H:/.../bin_patch.qpck", r"H:/.../bin.qpck"])
data = ma.read_path("some/resource.bin")   # 自动命中优先级最高的归档
```

## 6. 已验证 / 未验证清单

区分这两类是本项目的硬性纪律：**不要把推测写成定论**。

### 6.1 已验证 ✅

> **验证规模（重要）**：下表的前 6 项最初只在 `conf.qpck`（仅 5 个条目）上验证过。
> 现已对**全部 8 个真实归档**（含 92,090 / 144,142 条目的 `bin.qpck`）重新裁决，
> 全部通过严格布局校验。因此它们不再是"小样本推测"。
> Scale note: the first six rows below were initially validated only on conf.qpck (5 entries).
> They have since been re-adjudicated against all 8 real archives (including 92,090- and
> 144,142-entry bin.qpck) and all pass strict layout validation. They are no longer
> small-sample inferences.

| 断言 | 验证方式 |
|---|---|
| magic 为 `0x37402858` | 8 个真实归档头部比对 |
| `count` 为 i32 LE | 与 C# 参考实现的 `ReadInt32` 一致，且 8 个样本自洽 |
| TOC 每条 20 字节 = i64+u64+i32 | 20 字节步长，结构自洽 |
| 数据区紧贴 TOC 且连续无填充 | **8/8 归档通过严格校验**：每个 `offset` 精确等于上一块末尾 |
| 末块末尾 == 文件大小 | 同上，`end == size` 在 8/8 归档上成立 |
| TOC 按 hash 升序 | **8/8 归档全部升序**（见下表） |
| **重复 hash 处理为"先入为主"** | 见下方 §6.1.1 —— 已在真实 patch 数据上验证 |
| 包装/解包可字节级往返 | 见 §8 |

### 6.2 未验证 ⚠️

| 断言 | 现状与证据强度 |
|---|---|
| 引擎用**二分查找**定位 TOC 条目 | 有序性强烈暗示，因为 `bin.qpck` 有数十万条目，线性扫描会慢。但**没有反汇编证据**。我们的保守对策：一律按 hash 升序输出，二分和线性扫描都能正常工作 |
| `count` 字段实际能否为负 ⚠️ | 结构上可以，但没有样本支持，也看不出有此用法 |
| 重复 hash 的处理是"先入为主" | 这是我们对齐引用的 C# 实现行为（`if (!_toc.ContainsKey(...))` 后再 Add），**未在真实 exe 上验证**。考虑到 mod 覆盖依赖这条语义，优先级高，待验证 |
| 是否存在本引擎之外的其它 qpck 变体 | 目前只见过 PC 版两作；PSP/PSV/PS4 是否有同名格式未知（项目目标是 PC，此点优先级最低） |

#### 6.1.0 全量布局审计（8 个真实归档）

对每个归档只读取 TOC（每条目 20 字节，不做数据区 IO），因此对数 GB 归档也是毫秒级：

| 游戏 | 归档 | 条目数 | 按 hash 升序 | 重复 hash | 长度 0 条目 | 严格布局校验 |
|---|---|---|---|---|---|---|
| GER | `bin_patch.qpck` | 101 | ✅ | 0 | 0 | ✅ OK |
| GER | `bin.qpck` | 92,090 | ✅ | 0 | 0 | ✅ OK |
| GER | `conf.qpck` | 5 | ✅ | 0 | 0 | ✅ OK |
| GER | `data.qpck` | 56,273 | ✅ | 0 | 0 | ✅ OK |
| GE2RB | `bin_patch.qpck` | 482 | ✅ | 0 | 0 | ✅ OK |
| GE2RB | `bin.qpck` | 144,142 | ✅ | 0 | 0 | ✅ OK |
| GE2RB | `conf.qpck` | 5 | ✅ | 0 | 0 | ✅ OK |
| GE2RB | `data.qpck` | 110,013 | ✅ | 0 | 0 | ✅ OK |

**一个重要发现**：8 个归档里**没有任何一个存在重复 hash**（dups 全为 0）。
这说明"去重/先入为主"不是单文件内的一个特性，而是**跨文件的叠加层语义**——
每个 qpck 自身是干净的，重复只会在多个归档合并时才出现。

#### 6.1.1 「先入为主」覆盖语义：首次用真实数据验证

这是"mod 如何生效"的核心机制，此前只是引用参考实现的行为，**没有独立验证**。
现用真实 patch 数据裁决：

| 游戏 | patch 条目 | 与后续归档重叠 | 解析成功 | 返回的是不是 patch 副本 |
|---|---|---|---|---|
| GER | 101 | **101（全部）** | 101/101 | 抽样 50 → **50/50 是** |
| GE2RB | 482 | 11 | 11/11 | **11/11 是** |

结论：`MultiArchive` 在patch 与后续归档存在相同 hash 时，返回的是**靠前归档的副本**。
mod 覆盖机制成立。

**连带发现（此前未知）**：两作使用 patch 的方式完全不同——
- **GER**：101 个 patch 条目 **全部**覆盖已有的原版条目 ⇒ 纯替换型补丁。
- **GE2RB**：482 个里只有 11 个是替换，其余 **471 个是新增** ⇒ 以增量内容为主。

这意味着给两作做 mod 时，`bin_patch` 的用法并不相同，不可照搬。

## 7. 名字表：当前的最大缺口

如前所述，qpck 不存文件名。我们需要一份外部的"路径→哈希"名字表来：

1. 让解包产物有可读的文件名
2. 让我们能**打包出游戏真正认的** qpck

### 候选来源（按性价比排序）

| 来源 | 可行性 | 说明 |
|---|---|---|
| **PRES 资源树**（推荐） | 高 | PRES 是资源的索引层，沿着 PRES 递归即可导出资源的路径名。这是我们下一阶段的目标格式 |
| `.i64` IDA 数据库中的字符串 | 中 | 两个游戏的 `*.i64` 已经存在（456MB/480MB），前人已完成分析。字符串表里可能包含资源路径列表 |
| exe 内的路径字符串 | 中 | 直接用二进制搜索即可，成本低 |

> **验证办法很直接**：任何候选路径，只要 `crc64(normalize(path))` 等于某个真实的
> TOC 哈希，就是自证的。用 `python -m tools.qpcktool hash <path>` 可以立即检验。

## 8. 端到端验证

下面这条流程在当前仓库状态**已经跑通**，是回归测试的基础：

```bash
# 1. 查看归档信息
python -m tools.qpcktool info <file.qpck> --list

# 2. 解包（生成 manifest.jsonl）
python -m tools.qpcktool unpack <file.qpck> --out work/extracted

# 3. 重新打包
python -m tools.qpcktool pack --manifest work/extracted/manifest.jsonl --out work/new.qpck

# 4. 与原文件逐字节比对
python -m tools.qpcktool verify <file.qpck> --dir work/extracted --source <file.qpck>
```

### 8.1 实测结果

| 样本 | 大小 | 条目数 | 往返字节一致 |
|---|---|---|---|
| GER `conf.qpck` | 53,712 B | 5 | ✅ SHA256 一致 |
| GER `bin_patch.qpck` | 34.9 MB | 101 | ✅ SHA256 一致 |
| GE2RB `conf.qpck` | 49,647 B | 5 | ✅ SHA256 一致 |
| GE2RB `bin_patch.qpck` | 69.7 MB | ? | ✅ SHA256 一致 |

> 说明：`bin.qpck`（6.87 GB）与 `data.qpck`（4.16 GB）尚未做完整往返（体积过大，
> 且 networked in IO 时间成本高）。结构上它们的头部与 `conf.qpck` 完全一致，
> 因此风险很低，**但这仍然是尚未执行的一步，不是已验证结论**。

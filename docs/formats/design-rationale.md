# 四种数据格式的设计意图（人类视角）

> **本文的定位**：不是字段手册（那些在各自的格式文档里），而是回答四个问题：
> **它们各自是干什么的？为什么需要它？为什么不合并成一种？为什么这样设计？**
>
> 读完这篇，应该能对「游戏数据在磁盘上到底长什么样、为什么要长这样」形成一张连贯的图。
>
> 如果觉得抽象，先看 [`pres-illustrated.md`](pres-illustrated.md) ——
> 那里有两个**完整文件**的逐字节解读（一个 384 字节的 PRES 含 tbl，一个 rtbl 的完整槽）。
>
> 字段级细节请查：
> [`pres.md`](pres.md) · [`kst1.md`](kst1.md) · [`tr2-reading.md`](tr2-reading.md) · [`qpck.md`](qpck.md)

---

## 0. 一句话版本

| 格式 | 一句话 | 类比 |
|---|---|---|
| **qpck** | 一个巨大的**哈希表**：`CRC64(路径) → 字节块` | 没有目录的压缩包 / 内容寻址存储 |
| **PRES** | 对 qpck 的**目录与索引**：告诉你"有哪些资源、叫什么、在哪" | tar 的 TOC / 文件系统 inode 表 |
| **tbl** | PRES 里的一种**小整数数组**：用下标指向同目录的其他资源 | 符号表 / 跳转表 |
| **rtbl** | 一串**固定步长的引用槽**：每个槽登记一个资源 | 索引数组 / 指针表的平铺版 |
| **kst1** | 引擎自带的**键值数据库**：`u32 key → 定长记录` | 简易 B 树 / 稀疏索引 |
| **tr2** | **列式数据表**：每个字段自带一整列数据 | 列存数据库 / 结构体数组的转置 |

其中 **PRES / tbl / rtbl** 是"资源层"（管**文件在哪**），
**kst1 / tr2** 是"数据层"（管**游戏规则数值**）。这是理解全局的第一刀。

---

## 1. 为什么要分成这么多层

### 1.1 一个反直觉的事实：PC 版不用文件系统目录

打开游戏目录，只有 4 个 `.qpck` 和 1 个 `.exe`。所有资源——几万个贴图、音频、表格——
全在几个 GB 级的大包里。**没有 `data/textures/xxx.png` 这样的目录树。**

原因不是"懒得整理"，而是**加载性能**：

- 一个大文件可以**顺序预读**，机械硬盘 / 光驱上远比随机打开几万个小文件快；
- 资源之间大量**共享同一份数据**（同一个贴图被 6 个语言版本、几十个场景引用），
  放成独立文件会重复占空间；
- **补丁替换**只需换一个包里的一个条目，不用改动目录结构。

qpck 就是这个"大包"，PRES 就是它的**目录**。

### 1.2 四层的分工

```
qpck        我有什么数据块？        （内容寻址：按哈希找）
  └ PRES    这些数据块各自是什么？   （语义：名字、类型、归属）
      ├ tbl   哪些资源要一起用？     （同目录内的下标数组）
      ├ rtbl  哪些资源要一起用？     （跨目录的槽表）
      └ 叶子资源
          ├ kst1  键值型配置       （稀疏 key → 定长记录）
          └ tr2   表格型配置       （字段 → 整列数据）
```

**为什么资源和数据要分两层？**
资源是"**字节**"（一张贴图 200KB，你只需要搬它，不需要懂它）；
数据是"**语义**"（怪物攻击力 172，你要读出来算伤害）。前者由打包工具管，后者由游戏逻辑管。

## 2. PRES：唯一能把哈希翻译回名字的东西

### 2.1 它解决什么

qpck 的目录只存 `CRC64(路径)`，**不存路径字符串本身**。这是内容寻址存储的经典权衡：

- ✅ 省空间（8 字节 vs 平均 60 字节路径 × 十几万条）
- ✅ 天然去重（同名资源自动合并）
- ❌ **丢失了可读性**——你拿到一堆 16 进制哈希，不知道哪个是哪个

PRES 就是补偿这个损失的**索引层**：它存着完整路径字符串、资源类型、以及数据的存放方式。

### 2.2 为什么它长成"8 组 + 语言分组"

PRES 内部有两层分组，都有明确的现实动机：

**外层 = country（1 或 6 个）**
游戏要发 6 种语言。文本必须分开，但**贴图和音频不需要**。
所以 PRES 允许一个文件带 1 组或 6 组数据——单语言资源就只存 1 份，
只有真正需要翻译的文本才复制 6 份。实测 GER 里 3,972 个文件是 1 组、4,614 个是 6 组。

**内层 = 8 个 dataset**
这是按"**资源怎么被使用**"分的，不是按文件类型分的。

> **命名约定**：组名（`prx` / `asset` / `conf` …）只是标签，**不代表内容**。
> 例如 `asset` 里也有 B 型外部引用，`conf` 里装的绝大多数不是 `.conf` 文件。
> 为避免误解，本文统一用 **`res.<组名>`** 的写法指代"某个组"。

| # | 组名 | 统一写法 | 实测内容（扩展名 top） | 一句话本质 |
|---|---|---|---|---|
| 0 | `res` | `res.res` | 100% `.res` | 子 PRES（继续往下走） |
| 1 | `prx` | **`res.prx`** | 100% `.prx` | 外部模块声明（类似 DLL） |
| 2 | `asset` | **`res.asset`** | `gnf` 455,619 / `ixo` 163,421 / `is14` 75,584 / `tr2` 53,172 | **被 tbl 下标索引的数组**（F 内嵌 + B 引用混放） |
| 3 | `unk` | `res.unk` | 空 | 预留 |
| 4 | `conf` | **`res.conf`** | `res` 14,078 / `gnf` 3,830 / `is14` 2,840（真 `.conf` 仅 48 条） | **不被下标索引的登记簿**（纯 B） |
| 5 | `tbl` | **`res.tbl`** | 无扩展名 | **小整数数组**（下标表） |
| 6 | `text` | **`res.text`** | 无扩展名 | 文本（按语言分开） |
| 7 | `rtbl` | **`res.rtbl`** | 100% `.rtbl` | 指向 qpck 里的槽表文件 |

> 注意 `tbl` 不是"表文件"，而是"**一张小的整数数组**"。真正的业务大表在 `tr2` 里。
>
> ⚠️ **`res.conf` 里 99.8% 不是 `.conf` 文件**（实测 48/24,979）。组名 `conf`
> 是历史命名，它的真实含义是"只登记路径、不带数据的资源"。详见 §3.2.1。

### 2.3 为什么条目有三种类型（0 / B / F）

这是"**数据和索引分离**"的直接结果：

| 类型 | 含义 | 为什么需要 |
|---|---|---|
| `B` 引用 | 只有一条路径字符串 | 数据在 qpck 里，PRES 只记"去哪拿" |
| `F` 数据 | 数据**内嵌**在 PRES 里 | 小数据（几字节的表、短文本）不值得单独进 qpck |
| `0` 占位 | 有名字、无数据 | **保持数组下标稳定**（见 §3.2） |

**为什么要 F（内嵌）？** 如果每个 3 字节的表也要走 qpck，就要为它建一个哈希条目、
一次随机读取。内嵌在 PRES 里，读 PRES 时**顺带就读到了**。

**为什么要 0（占位）？** 这不是浪费，而是刻意的——它让"数组下标"成为稳定的标识符。
详见 §3.2。

### 2.4 为什么资源要套层：一个 384 字节样本的证据

这是最容易被质疑的设计决策：**上级包为什么不直接引用最终文件，而要绕一层子 PRES？**

用一个真实样本回答。

#### 2.4.1 样本

```
子包  GameFace.res                        384 字节，countryCount = 1
  └ ds2(asset):  GameFace.ixo.blz           （外部引用 B 型）
  └ ds5(tbl)  :  List_tbl = [0]             （指向上面那条）

父包  god_menu.res                    6,033,088 字节，countryCount = 6
  └ ds4(conf) :  .../NPC_004N_Soma/GameFace.res    ← 引用的是 .res
```

#### 2.4.2 实测：上级包根本不认识最终文件

| 检查 | 结果 |
|---|---|
| 谁引用了 `GameFace.res` | 只有 `god_menu.res`，通过 **ds4(conf)** |
| 引用了几次 | **6 次**（6 个 country 各 1 次） |
| 6 次的 ref 字符串 | **完全相同**（去重后 1 个值） |
| 父包里直接登记 `GameFace.ixo.blz` 的条目 | **0 条** |

**父包里压根不存在 `GameFace.ixo.blz` 这个路径。** 它只出现在子包内部。

所以"为什么上级包不直接调"的答案是：**它没有这个能力**——不是不想，是不能。

#### 2.4.3 三个硬约束

**① 语言维度错配（最主要原因）**

```
父包 god_menu.res  : countryCount = 6
子包 GameFace.res  : countryCount = 1
```

全库这个模式极为普遍：

| (子包 cc, 父包 cc) | 引用次数 |
|---|---|
| **(1, 6)** | **7,308** |
| (6, 6) | 18,114 |
| (1, 1) | 355 |
| (6, 1) | 20 |

**7,308 次是"父包 6 语言、子包无语言"的引用。**

若把模型直接登记进父包的 ds2：父包有 6 个 country，**每个 country 都有自己的数组**，
于是同一个模型要在 6 个 country 里各登记一次——路径重复 6 份，且必须保证 6 份一致。

用子包则：6 个 country 的 ds4 各加 1 条，**都指向同一个 384 字节的子包**。

**核心价值：把"语言无关的内容"从"6 语言的容器"里摘出去。**

**② 资源天然成组**

`GameFace.res` 这个样本恰好只有 1 个文件，是简化样本。真实的"一张脸"通常包含
模型、贴图、表情、骨骼。上级包需要的是**一个整组句柄**，不是其中某一个文件。

**③ 补丁粒度**

`god_menu.res` 有 6 MB。若所有 NPC 的脸都平铺在里面，改任何一张脸都要重写 6 MB；
现在只需替换 384 字节的 `GameFace.res`。

#### 2.4.4 `List_tbl` 不是"全部资源清单"

一个容易想当然的误解：以为 `List_tbl` 就是"本包所有资源"。

实测 791 个 PRES 含 `List_tbl`：

| 情况 | 数量 |
|---|---|
| `List_tbl == [0,1,…,n-1]` 且 `n == ds2 条目数`（完整清单） | **80** |
| 其它（部分 / 乱序 / 不等长） | **711** |

样本：

```
Before.res   List_tbl = [11, 12]    ds2 = 13 条   ← 只列了 2 个
After.res    List_tbl = [11]        ds2 = 12 条
Before.res   List_tbl = [31, 32]    ds2 = 33 条
```

**78% 的情况只选了一部分。** 所以 `List_tbl` 的准确语义是
"**某个特定用途需要的那几个**"，而不是"全部"。

这也反过来解释了子包的另一个作用：它既提供**封装**（上级只认 1 个句柄），
也提供**内部组合表达**（`List_tbl` 说"这次用哪几个"）。两件事上级包都做不到。

## 3. tbl：用下标表达"哪些资源要一起用"

### 3.1 功能

`tbl` 的载荷是**一串 u32**，没有表头。它的用途是表达**资源之间的组合关系**：

```
SystemSe_tbl = [12, 13, 14, 15, 16, 17, 18, 19, 20]
                ↓ 每个数字是 asset 组的数组下标
            SE_SYS_ENTER1, SE_SYS_CANCEL1, SE_SYS_SELECT1, ...
```

翻译成人话：**"系统音效这一组，由这 9 个音频文件组成。"**
游戏要预加载系统音效时，读这张表，按下标把 9 个文件都取出来。

**这是"资源清单"而不是"资源数据"。** 它不解码任何东西，只负责把一堆资源**点名**。

### 3.2 为什么用"下标"而不是"名字"或"哈希"

这是 tbl 最值得理解的设计决策：

| 方案 | 代价 |
|---|---|
| 存路径字符串 | 每条 60 字节，一张 100 项的表要 6KB |
| 存 CRC64 哈希 | 每条 8 字节，但要查表才能用 |
| **存数组下标** | **每条 4 字节，且取用时是 O(1) 直接寻址** |

下标方案的代价是**脆弱**：一旦 asset 数组增删一个元素，所有后续下标全部错位。

**所以 `type 0` 占位条目存在的真正原因就在这里**：删掉一个资源时，
不是从数组里移除，而是把该条改成 `type 0`（无名字、无数据），**占住这个位置**。
这样所有 tbl 的下标都还有效。

> ⚠️ **这是改包时最容易翻车的地方**：看到 type 0 空条目以为是垃圾删掉，
> 实际会让后续所有 tbl 索引错位，游戏读到的资源全错。

### 3.2.1 为什么 `asset` 组里混着 F 和 B 两种类型

这是最容易被误解的一点。看到"asset 是资源主体"，会觉得里面应该全是内嵌数据（F），
但实测 `ds2(asset)` 有 **145,140 条 B 型**（外部引用）。为什么不把这些 B 挪到 `conf`？

**实测原因**：

```
ds2 的 B 型条目 = 24,770
  其中被本 PRES 的 tbl 按下标引用到 = 10,035（40.5%）
  引用路径首目录：bin 23,333 / data 1,437
```

**40.5% 的 ds2 B 型条目正被 tbl 按下标引用。一挪走，那些表全废。**

所以 ds2 的规则不是"装内嵌数据"，而是：

> **ds2 是"tbl 可以按下标索引的数组"。为了下标连续稳定，
> 这个数组里只放"需要被 tbl 点名的东西"，不管它是内嵌（F）还是外部（B）。**

对照 ds4(`conf`)：实测只有 2,174 张表用它做宿主（vs ds2 的 192,781），
说明 **ds4 基本上不被下标引用**，所以 `conf` 里的条目可以随便增删。

**一句话**：

| 组 | 本质 | 能否随便增删条目 |
|---|---|---|
| `ds2 asset` | **被下标引用的数组** | ❌ 会破坏 tbl |
| `ds4 conf` | **不被下标引用的登记簿** | ✅ 没人按下标指它 |

### 3.2.2 一张 tbl 只服务一个组（实测）

**能否一张 tbl 同时索引 ds2 / ds4 / ds6？实测：不能。**

```
值域同时落在 2+ 个组内的 tbl = 4,897
  其中『两组都能对上名字』的 = 4        ← 0.08%，极可能是判据误报
只落在一个组内的 = 54,946
```

那 4,897 张"跨组"是因为短表的值很小，落在哪个组都不会越界——
但**语义上只有一组能对上名字**。

**结论：单宿主。** 而且文件里**没有任何字段**说明它服务哪个组（§8.5.1 已证无表头），
完全由消费者代码决定。


### 3.3 为什么"形状"不在文件里

tbl 载荷是纯数组，**没有"每行几个字段"的信息**。那读取方怎么知道怎么解释？

答案是：**读取它的代码知道。** 证据很硬——同族表的长度高度恒定：

| 表族 | 实例数 | 载荷长度 |
|---|---|---|
| `ScriptSetup` | 4,879 | **恒 7 个 u32** |
| `PC_Face_obj` | 4,639 | **恒 3 个 u32** |
| `bgm00_obj` | 4,092 | **恒 2 个 u32** |

`ScriptSetup` 在 4,879 个**不同的 res 文件**里长度都是 7——这只能是代码里写死的结构体布局。

**翻译成人话**：`PC_Face_obj` 就是引擎里的 `struct { u32 a, b, c; } face_obj;`，
而文件里只是把这个结构体的字段**依次摊平**成 7 / 3 / 2 个 u32。
文件本身不描述结构，结构定义在 C 代码里——**这正是"格式"和"代码"耦合的地方**。

### 3.4 表和表怎么联系：一个函数说清一切

反汇编 `_resGetDatByTable`（`0x1DAA169`）给出了唯一机制：

```c
// 在"某一组的 entry 数组"里，按名字线性查找
for (i = 0; i < count; i++) {
    entry = groupArray[ table[i] ];       // ← table[i] 就是下标
    if (entry->names[0] == targetName)
        return entry;
}
```

两个包装函数分别传入 **group 2（asset）** 和 **group 0（res）**。

实测全库：**192,781 条走 group 2**（asset），另有 2,174 条走 group 4（conf）、
72 条走 group 6（text）。`GameBgm_tbl` 是个漂亮的反例——只有 group 4 能解释它：

```
GameBgm_tbl = [15, 16, 6, 7, ...]
  按 group 2 解释 → SE_SYS_ERROR1 ... （语义不符，且越界）
  按 group 4 解释 → bgm_result, bgm_god_eater_resurrection, bgm_anagura_001 ...  ✅完美
```

**结论**：tbl 的宿主不是文件自描述的，而是**由消费代码决定**。
同一个 PRES 里，音效表用 asset 组、BGM 表用 conf 组。这看起来不一致，
但其实是合理的——**读的人知道自己在读什么**。

## 4. rtbl：tbl 的"跨目录版本"

### 4.1 功能

rtbl 和 tbl 目的相同（点名一组资源），但形态不同：

| | tbl | rtbl |
|---|---|---|
| 存放 | 内嵌在 PRES 里 | **独立文件**，在 qpck 里 |
| 元素 | 4 字节**整数下标** | **0x200 字节的槽**，内含路径字符串 |
| 指向 | 同 PRES 同 country 的资源 | **任意位置**的资源（含其他 PRES 的子资源） |
| 典型用途 | 音效组、UI 部件、脚本配置 | **语音、音乐**这类跨场景/跨目录的大宗资源 |

### 4.2 为什么需要 rtbl 而不都用 tbl

因为 **tbl 的下标只能指向"同一个 PRES 的某个组"**——它指不到外面去。

但语音资源是**跨场景共享**的：`cmn_0400_Tsubaki.is14` 在 `event/Demo_middle/` 目录下，
可能被几十个任务引用，它不在任何一个任务的 PRES 里。要登记这种"跨目录引用"，
下标就不够用了，必须能写**完整路径**。

**实测佐证**：`god_menu.res` 的 rtbl 里 45 个非空槽，
**没有一个**指向本 PRES 自己的资源，全部是外部资源。

**所以 rtbl 的槽直接存路径**——代价是每个槽 0x200 字节，比 tbl 的 4 字节贵 128 倍，
但换来了"能指向任何地方"。

**成本对比（实测）**：

| | 用 tbl / conf | 用 rtbl |
|---|---|---|
| 最大的一张 rtbl（角色头像） | 需 9,991 条 entry（32B 头 ≈ 320 KB + 名字区） | **1 条 entry** + 一个 6 MB 独立文件 |
| Kouta 语音库（45 条） | 需 45 条 entry，挤进 ds4 数组 | **1 条 entry** + 一个 569 KB 独立文件 |
| 被多个 PRES 共享 | ❌ 每个 PRES 都要复制一份 | ✅ 共享同一个 rtbl 文件 |
| 单独替换（mod） | ❌ 要重写整个 PRES | ✅ 只换那个 .rtbl 文件 |

**规模差异是决定性的**：1 条 entry vs 9,991 条 entry。

### 4.2.1 tbl 和 rtbl 的槽位编号差异

rtbl 还有个 tbl 给不了的能力：**稳定的槽位编号**。

实测占位图（`Kouta_tbl.rtbl`，1,111 个槽只用 45 个）：

```
槽 400: ....................X.........X.........X.........X.........X.........X.........
槽 480: X.........X.....................................................................
```

所有 `X` 都落在**每 10 个位置的第 0 个**上（420, 430, 440, 450…）。
说明这个语音库为每个"语音编号"**预留了 10 个槽**，实际只用第 0 个。

游戏可以用「第 420 号槽」这种**稳定编号**点播语音。
而 tbl 只有"第几个元素"，增删一条就会移位。

### 4.3 槽为什么固定 0x200 字节

一个槽里放：`typeAndAddress(4) + size(4) + nameTableAt(4) + nameCount(4) + 保留(16)
+ 路径字符串(最多约 460 字节) + 4 个名字指针 + 名字池`。

固定 0x200（512 字节）的好处是 **O(1) 随机访问**：要第 i 个槽，直接 `base + i*0x200`，
不需要读前面的槽来算偏移。代价是**短路径会浪费空间**——
实测 176,469 个空槽（整槽全零），说明这个文件是**预留了增长空间**的。

> 空槽全零、非空槽 `+0x00` 恒为 `0xB0000020`（类型 B + 偏移 0x20）——
> 这是"槽结构"本身的高度规律性，全量 189,794 个非空槽 **无一例外**。

### 4.4 为什么 rtbl 还带 `_EXISTS=` 位图

rtbl 的 PRES 条目里有一个 `_EXISTS=` 属性，后面跟一个位图，**每一位对应槽是否被占用**。

**为什么需要它？** 因为 rtbl 文件可能有上千个槽，其中大部分是空的。
游戏加载时若要知道"这个 rtbl 里到底有哪些资源"，逐个槽去读路径是 O(n) 的磁盘访问。
有了位图，**一次读 140 字节就能知道 1,111 个槽里哪些非空**。

实测 4,614 条 `_EXISTS=` **逐 bit 精确等于**"该槽首 dword ≠ 0"，零例外。

## 5. kst1：引擎自带的键值数据库

### 5.1 它解决什么

有些数据天然是**稀疏的键值对**：

- 任务表：`任务ID → 任务的全部字段`（515 条，ID 不连续）
- 文本表：`文本ID → 文本内容`（13,162 条）

这类数据如果用 `tr2` 的列式表格存，会有大量空行；用数组存，ID 不连续会浪费空间。
**kst1 就是为这种场景设计的**。

### 5.2 为什么它这么"小气"

kst1 的核心是一个**两级索引 + 位图**结构：

```
头部（24 字节）
  stride      = 每条记录多少字节（如 312）
  numrecord   = 记录数（如 515）
  index_off   = 索引表位置
  record_off  = 记录表位置

索引表
  numBlocks   = 块数（如 80）
  maxKey      = 最大 key（如 20444）
  每块 36 字节：base + 256 位位图
```

查一个 key 的过程：

```
b = key / 256          → 第几个块
k = key % 256          → 块内第几位
if 位图[k] == 0:        → 不存在，直接返回
idx = base + popcount(位图, 0..k-1)   → 前面有多少个存在的 key
record = file + record_off + idx * stride
```

**精妙之处在于**：它**不存 key 本身**。它假设"key 在 `[0, maxKey]` 范围内相对稠密"，
于是用位图记录"哪些 key 存在"，用 `base + 前缀和` 算出"这个 key 的记录是第几个"。

- 空间：80 块 × 36 字节 = **2.8KB** 就能索引 20,444 个可能的 key
- 时间：两次乘法 + 一次 popcount，**O(1)**

如果改成"存一个 `key → offset` 的排序数组"，同样的信息要 515 × 8 = 4KB，
而且查找要二分。**位图方案在小 key 空间上更省、更快。**

### 5.3 一个容易踩的坑（也说明了设计的紧凑程度）

位图的位序是 **MSB-first**（`0x80000000 >> (k%32)`），与常见的 LSB-first 相反。
而且"每块 36 字节"这个数字，如果按 dword 指针算错，会读成 32 字节——**整张表全乱**。

这种"省到极致"的风格说明 kst1 是**为内存和速度优化过的运行时结构**，
而不是给人读的配置文件。

## 6. tr2：列式存储的业务数据表

### 6.1 它解决什么

游戏里绝大多数**业务数据**在 tr2 里：怪物属性、掉落、任务流程、武器参数…
（GER 有 19,486 条 tr2 资源，是占比最高的格式。）

一张典型的表，人类理解是"8 行 × 5 列"：

| 行 | 斩击 | 打击 | 火 | 冰 | 雷 |
|---|---|---|---|---|---|
| 0 | 2 | 0 | 0 | 0 | 0 |
| 1 | 6 | 0 | 0 | 0 | 0 |
| … | | | | | |

### 6.2 但它在磁盘上是"列式"的

tr2 的物理布局**不是**行式（`行0列0 行0列1 … 行1列0`），而是：

```
文件头
Field 表（5 条，每条描述一个"列"）
元数据区[斩击]：名字、类型 INT16、行数 8、偏移表、然后 8 个 INT16 数据
元数据区[打击]：同上
元数据区[火]  ：同上
...
```

**每个字段自带它的整列数据。**

为什么这么设计？三个理由：

1. **读一列只要一次连续读**。游戏要算"这批怪物的斩击抗性"时，
   列式存储让它只需读一个连续块，而行式要把每行的其他字段也读进来再丢弃。
2. **每列可以有独立类型和长度**。`斩击` 是 `INT16`、`名字` 是 `ASCII`、
   `时序数组` 是 `FLOAT32 × 4`——列式布局让每列独立处理，互不干扰。
3. **变长字段友好**。文本列长度不一，放在列内只需一个偏移表；
   放在行内会让整行变长，所有行都要跟着重排。

### 6.3 怎么读一个值

```
1. 从 Field 表找到字段 → 得到它的元数据区地址 meta
2. 读 meta+0x80 处的偏移表：offsets[row] 是第 row 个值相对 meta 的偏移
3. 值就在 meta + offsets[row]
```

偏移表长 `n+1` 项，第 `n` 项指向数据区末尾——**这也是变长处理的关键**。

### 6.4 为什么 tr2 有"主键"却没有"主键列"

这是 tr2 最关键、也最容易被误解的一点（现已完全解开）：

**tr2 的行没有独立的 ID 列。** 它的主键是一份**独立的排序索引数组**，
放在 Field 表之后：

```
+0x38  fieldTableOff
+0x3C  fieldCount
+0x40  Field 表，fieldCount × 20 字节
fieldTableOff + fieldCount*20
  +0x00  u32 count
  +0x04  u32[count] ids     升序、唯一
```

**为什么这样设计而不是加一个 ID 列？**

| 方案 | 代价 |
|---|---|
| 每行加一个 ID 字段 | 每行多 4 字节；且**按 ID 查找要线性扫描全表** |
| **独立的排序索引数组** | 额外 `4×(n+1)` 字节，但**按 ID 查找是二分 O(log n)** |

游戏运行时最常见的操作是"**给我 13688 号道具的所有字段**"。
有了排序索引，一次二分就知道它是第几条记录，然后去各列取第那个下标的单元格。
**ID 列方案做不到这一点**——除非再额外维护一份排序表，那还不如直接做成现在这样。

**翻译成人话**：主键不写在行里，而是写在**表头的一张对照表**里。
这就像一本书没有给每页编号，而是在目录里列出"章节→页码"。

全量验证：18,694 / 19,473 张表（**96.00%**）的索引数组完美升序且唯一，
累计 502,857 条记录。详见 [`tr2-primary-key.md`](tr2-primary-key.md)。

### 6.5 主键与"行号"是两套编号

~~ **tr2 的行没有独立的 ID。** ~~ 这句话在"行内没有 ID 列"这个意义上仍然正确，
但**表整体是有主键的**——它是一份独立的排序索引（见 §6.4）。

所以 `en_mat_article_id = 13688` 里的 13688 **不是行号**，
而是"道具系统里的那个 13688 号道具"。要找到它，去道具表的 **ID 索引数组**里二分，
得到记录序号，再取各列的值。

**这曾经是理解全部"表间关系"的关键障碍**：跨表引用用**业务 ID**，
而表内定位曾经只能用**行号**。现在两者的桥已经搭好。

### 6.6 kst1 与 tr2 的分工

| | kst1 | tr2 |
|---|---|---|
| 布局 | 行式（定长 stride） | **列式** |
| 定位 | 按 **u32 key**（位图 + 前缀和） | 按 **ID 索引**（排序数组 + 二分） |
| key 空间 | **稠密**（如文本 ID 0..20444） | **稀疏**（如道具 ID 1941, 13557） |
| 空表表示 | 位图全 0 | `count = 0` |
| 适合 | 键值对、变长文本 | 多字段、按 ID 查记录 |
| 典型 | 任务表、文本表 | 怪物、武器、掉落、任务流程 |

**选择依据很简单**：key 空间稠密 → kst1（位图最省）；
key 空间稀疏 → tr2（排序数组 + 二分，位图会产生巨大空洞）。

> 具体对比见 §7 与 [`tr2-primary-key.md`](tr2-primary-key.md) §5。

## 7. 为什么不能合并成一种格式

看到这里可能会问：既然都是"存数据"，为什么不统一？

因为它们的**优化目标不同**，而且互相冲突：

| 格式 | 首要目标 | 为此牺牲 |
|---|---|---|
| qpck | 存储密度 + 加载速度 | 丢失可读性（只有哈希） |
| PRES | 可发现性 + 补丁粒度 | 体积（多一层索引） |
| tbl | **下标寻址 O(1)** | 脆弱（靠 type 0 占位维持） |
| rtbl | 跨目录引用 | 空间（每槽 512 字节） |
| kst1 | 稀疏 key 的 O(1) 查找 | 只支持 u32 key、定长记录 |
| tr2 | 按列读取 + 变长字段 | 难以按行随机访问 |

**如果合并成"一种通用格式"**，就要在每一处都保留最贵的那个特性（路径字符串、
变长、随机访问），结果是**体积和内存同时爆炸**。这在一个要装进光盘、
运行在 2010 年代硬件上的引擎里是不可接受的。

**这四种格式的共同哲学是：把"定位"和"解读"分离。**
- qpck / PRES / tbl / rtbl 只解决"**东西在哪**"
- kst1 / tr2 只解决"**东西是什么**"

## 8. 从人类角度的一张总图

```
你想改一个怪物的攻击力。

1. 攻击力在哪？
   → 在某个 tr2 表里（如 en_atk.tr2 的 en_atk_slash 列）

2. 怎么找到那个 tr2 文件？
   → 它的路径在 PRES 的 asset 组里（一条 B 类型条目）
   → PRES 的路径 → CRC64 → qpck 里找到数据块

3. 谁引用这张 tr2？
   → 可能有 tbl 指向它（下标）、rtbl 指向它（路径）

4. 值怎么读？
   → tr2：Field 表 → 元数据 → 偏移表 → 值

5. 值代表什么？
   → 需要知道那一列的类型（INT16）和业务语义（斩击攻击力）
   → 业务语义不在文件里，在代码里 / 在表名和字段名里
```

**最后这一点是全篇的要点**：
这四个格式**只描述结构，不描述语义**。
"`en_atk_slash` 是斩击攻击力"这件事，文件里只有字段名 `en_atk_slash` 可供猜测，
真正的含义在游戏代码里。

所以逆向这些格式，永远是**两层工作**：
1. **格式层**：把字节读出来（已完成，四个格式都通了）
2. **语义层**：搞清楚每个字段是什么意思（进行中，靠字段名 + 运行观察 + 反汇编）

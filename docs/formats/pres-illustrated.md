# PRES 实战：完整文件逐字节解读

> **本文的定位**：前面所有文档都在讲"字段是什么"，但**看不到文件全貌**就很难建立直觉。
> 本文用**两个能完整看完的真实文件**，从第 0 字节到最后一字节，一次讲透 `tbl` 和 `rtbl`。
>
> 阅读顺序建议：先看 §1（tbl），再看 §2（rtbl），最后看 §3（为什么需要两种）。

---

## 0. 先建立一张地图

PRES 文件内部的所有东西，都是**层套层**的：

```
PRES 文件
├─ 32 字节头
├─ 8 个「组」= dataset（res / prx / asset / unk / conf / tbl / text / rtbl）
│   └─ 每个组里有一串「条目」entry
│       ├─ 条目头 32 字节（类型 + 地址 + 大小 + 名字位置）
│       ├─ 名字区（名字指针数组 + 字符串）
│       └─ 数据（内嵌，或一个路径指向别处）
└─ 尾部共享池（可选）
```

**关键：`tbl` 不是"表文件"，`rtbl` 也不是"表文件"。**
它们都是**PRES 里的一个组**，组里装着若干条目；每个条目指向的东西，才是真正的表数据。

## 1. tbl：完整解读一个 384 字节的 PRES

### 1.1 选这个文件的原因

`bin/resconv_pc/data/GameData/npc/model/NPC_004N_Soma/GameFace.res`
—— **384 字节**，是整个游戏里最小的、同时含 `asset` 和 `tbl` 的 PRES。
可以一屏看完，且结构完整。

### 1.3 逐段拆解

**① 头部 32 字节（0x00–0x1F）**

| 偏移 | 值 | 含义 |
|---|---|---|
| `0x00` | `50 72 65 73` | magic "Pres" |
| `0x08` | `08` | format = 8 |
| `0x09` | `03` | version = 3（引擎硬校验） |
| `0x0C` | `01 00 00 00` | sign = 1 |
| `0x10` | `80 01 00 00` | **pkgSize = 0x180 = 384**（= 文件全长，说明没有尾部池） |
| `0x1C` | `01 00 00 00` | **countryCount = 1** ⇒ 没有 country 表，body 从 `0x20` 直接开始 |

**② 8 个 dataset 目录槽（0x20–0x5F，共 64 字节）**

每槽 8 字节：`(条目头数组偏移 u32, 条目数 u32)`

| 组 | 偏移 | 值 | 含义 |
|---|---|---|---|
| 0 `res` | `0x20` | `0, 0` | 空 |
| 1 `prx` | `0x28` | `0, 0` | 空 |
| **2 `asset`** | `0x30` | **`0x60, 1`** | 1 条，条目头在 `0x60` |
| 3 `unk` | `0x38` | `0, 0` | 空 |
| 4 `conf` | `0x40` | `0, 0` | 空 |
| **5 `tbl`** | `0x48` | **`0x80, 1`** | 1 条，条目头在 `0x80` |
| 6 `text` | `0x50` | `0, 0` | 空 |
| 7 `rtbl` | `0x58` | `0, 0` | 空 |

> **这就是"组"的全部含义**：8 个槽，告诉你"哪个组在哪个位置、有几条"。

**③ ds2(asset) 的 1 条 entry（0x60–0x7F）**

```
0060  a0 00 00 b0   00 00 00 00   f0 00 00 00   04 00 00 00
```

| 偏移 | 值 | 含义 |
|---|---|---|
| `+0x00` | `0xB00000A0` | **类型 B（引用）**，地址 `0x0A0` |
| `+0x04` | `0` | dataSize = 0（B 型不用） |
| `+0x08` | `0xF0` | 名字指针数组在 `0xF0` |
| `+0x0C` | `4` | 4 个名字项 |

- `0x0A0` 处的字符串 = `"bin/resconv_pc/data/.../GameFace.ixo.blz"` —— **这是它引用的资源**
- `0xF0` 处的 4 个指针 → `"GameFace"`、`"ixo"`、`""`、`"bin/.../GameFace.ixo"`

> 注意：**这是 B 型（外部引用）**，但它**在 ds2 里**。所以 ds2 不只有内嵌数据。

**④ ds5(tbl) 的 1 条 entry（0x80–0x9F）—— 本文主角**

```
0080  60 01 00 f0   01 00 00 00   70 01 00 00   01 00 00 00
```

| 偏移 | 值 | 含义 |
|---|---|---|
| `+0x00` | `0xF0000160` | **类型 F（内嵌数据）**，地址 `0x160` |
| `+0x04` | `1` | **dataSize = 1** —— 注意：**单位是 u32 个数，不是字节** |
| `+0x08` | `0x170` | 名字指针数组在 `0x170` |
| `+0x0C` | `1` | 只有 1 个名字（表名，没有路径） |

**⑤ 真正的内容（0x160）**

```
0160  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

**就这 4 个字节**（其余是 16 对齐的填充）。读成 u32 = **`[0]`**。

**⑥ 名字（0x170）**

```
0170  74 01 00 00  4c 69 73 74 5f 74 62 6c 00 00 00 00
      ↑指针=0x174  "List_tbl\0"
```

`0x174` 处是 `"List_tbl"` —— **这张表叫 `List_tbl`**。

### 1.4 这个 tbl 到底是什么意思

```
文件名：GameFace.res                       （某个 NPC 的脸）
组 ds2(asset)：1 条，下标 0
    → GameFace.ixo.blz                    （脸的模型，外部引用 B 型）
组 ds5(tbl) ：1 条，名字 "List_tbl"
    → 载荷 = [0]                          （1 个元素，值是 0）
```

**`List_tbl = [0]` 的含义**：指向 **ds2(asset) 的第 0 条**，
也就是 `GameFace.ixo.blz` 这个模型文件。

**完美自洽。** 这个 PRES 表达的是：

> 「`GameFace.res` 这个资源包里，`List_tbl` 这一组包含 1 个资源：
> 本包 ds2 里的第 0 号，即 `GameFace.ixo.blz`」

而 `GameFace.ixo.blz` 是 **B 型**（外部引用），它的真实数据在 qpck 里，
路径由 entry 的 `0x0A0` 处字符串给出。

> ⚠️ **但 `List_tbl` 不总是"全部资源清单"**。实测 791 个含 `List_tbl` 的 PRES 中，
> 只有 **80** 个是 `[0,1,…,n-1]` 形式的完整清单，其余 **711** 个只列了一部分
> （例如某包 ds2 有 13 条，`List_tbl` 只写了 `[11,12]`）。
> 所以它的准确语义是"**某个用途需要的那几个**"，不是"全部"。
> 详见 [`design-rationale.md`](design-rationale.md) §2.4.4。

### 1.5 一个更典型的例子（多个元素）

`GameFace.res` 只有 1 个元素，不容易看出"数组"的感觉。
换入口 PRES 的 `SystemSe_tbl`（结构完全相同，元素更多）：

```
ds5 条目头：  类型 = F，dataSize = 9，名字 = "SystemSe_tbl"
载荷 @0x76E0：0c 00 00 00  0d 00 00 00  ...  14 00 00 00
             = [12, 13, 14, 15, 16, 17, 18, 19, 20]

查本 PRES 的 ds2(asset)（共 67 条）：
  [12] SE_SYS_ENTER1    F  1968B  is14
  [13] SE_SYS_CANCEL1   F   648B  is14
  [14] SE_SYS_SELECT1   F   528B  is14
  [15] SE_SYS_ERROR1    F   768B  is14
  [16] SE_SYS_WINDOW1   F  1248B  is14
  [17] SE_SYS_PAGE1     F  1608B  is14
  [18] SE_SYS_SELECT2   F  2243B  is14
  [19] SE_SYS_CANCEL2   F  1728B  is14
  [20] SE_SYS_PAGE2     F  1128B  is14
```

**`SystemSe_tbl` 的含义**：

> 「**系统音效这一组，由 ds2 里第 12 到第 20 条这 9 个资源组成**」

到这里 tbl 就完全清楚了：

- **它就是一张"号码表"**，每个号码是"本 PRES 里某个组的下标"
- **没有任何表头**（没有"本表指向哪个组"的字段）
- **指向哪个组由读取它的代码决定**
- `dataSize` 记的是**元素个数**，载荷本身只是一串裸 u32，没有长度前缀

## 2. rtbl：完整解读一个槽

### 2.1 rtbl 和 tbl 的根本差别

先看它们在 PRES 里长什么样：

| | tbl | rtbl |
|---|---|---|
| 条目类型 | **F**（数据内嵌在这个 PRES 里） | **B**（只是一个路径引用） |
| 数据在哪 | 就在 PRES 内部 | **在 qpck 里的一个独立文件** |
| 数据形态 | 一串 4 字节整数 | 一堆 **512 字节的槽** |

所以理解 rtbl 要分两层：

```
第 1 层：PRES 的 ds7 里有一条 B 型条目
         类型=B, size=目标文件字节数, 路径=".../xxx_tbl.rtbl"
              ↓ 按路径去 qpck 取
第 2 层：那个 .rtbl 文件，是 N 个 512 字节的槽
         每个槽 = 一条完整的"引用声明"
```

### 2.2 完整的一个槽（512 字节，全部有内容，不是全零）

取自 `god_menu_Voice_Generic_Kouta_tbl.rtbl` 的**槽 420**：

### 2.3 四个头字段的含义

| 槽内偏移 | 值 | 含义 |
|---|---|---|
| `+0x00` | `0xB0000020` | **类型 B（引用）** + 路径在槽内偏移 `0x20` |
| `+0x04` | `0` | dataSize（B 型不用） |
| `+0x08` | `0x70` | 名字指针数组在槽内偏移 `0x70` |
| `+0x0C` | `4` | 4 个名字项 |
| `+0x10`–`+0x1F` | 全 0 | 保留 |
| `+0x20` | 字符串 | **★ 它引用的资源路径** |
| `+0x70` | 4 个 u32 指针 | 指向 `0x80` / `0x91` / `0x96` / `0x97` |
| `+0x80` 起 | 字符串池 | `"cmn_0400_Tsubaki"` / `"is14"` / `""` / 完整路径 |

**四个名字**（和 PRES entry 的 names[] 完全同构）：

```
names[0] = "cmn_0400_Tsubaki"      基名
names[1] = "is14"                  扩展名
names[2] = ""                      空
names[3] = "data/GameData/event/.../cmn_0400_Tsubaki.is14"   完整路径
```

### 2.4 一个槽 = 一条"我要引用这个文件"的声明

**这就是 rtbl 的全部内容**：

> 「我（这个 PRES）需要 `data/GameData/event/Demo_middle/common/Sound/common/cmn_0400_Tsubaki.is14` 这个文件」

**注意这个路径**：`data/GameData/event/Demo_middle/...` —— 它**不在** `god_menu` 的资源树里。

实测：这个 rtbl 的 45 个非空槽，**没有一个**指向本 PRES 自己的资源，全部是外部资源。

**空槽长什么样**：整槽 512 字节全零。就这么多，没有任何"空标记"字段。

## 3. 为什么需要两种：一句话对比

把上面两个实例并排：

```
tbl（GameFace.res 里）：
  PRES 内部 4 个字节 = [1]
  → 意思是「用本组第 1 号资源」
  → 前提：资源必须已经在同一个 PRES 的某个组里
  → 4 字节就能表达一条引用

rtbl（god_menu.res 里）：
  PRES 里 1 条 B 型条目 → 指向 qpck 里一个 568,832 字节的文件
  文件里 1,111 个槽，每槽 512 字节，其中 45 个有内容
  → 每个槽 = 一条「我要引用这个外部文件」的声明
  → 512 字节才能表达一条引用
```

**为什么 tbl 这么省而 rtbl 这么贵？** 因为：

| | tbl | rtbl |
|---|---|---|
| 引用目标在哪 | **同一个 PRES 里** | **任何地方**（别的 PRES / qpck / 外部文件） |
| 用什么定位 | 数组下标（4 字节） | 完整路径字符串（最多 ~460 字节） |
| 能否应付目标不在本包 | ❌ | ✅ |

**tbl 的 4 字节只能指"附近的"，rtbl 的 512 字节可以指"任意远的"。**

而语音正好是"任意远的"：`cmn_0400_Tsubaki.is14` 在 event 目录下，
被 `god_menu`、战斗场景、剧情场景……**多个 PRES 共享**。
用 tbl 的话，每个 PRES 都得把那个文件复制一份到自己组里；用 rtbl 则共享同一个槽表。

## 4. 一句话速查

| 问题 | 答案 |
|---|---|
| tbl 在 PRES 里长什么样 | ds5 里的一条 **F 型**条目，载荷是**一串 u32** |
| tbl 那串 u32 是什么 | **某个组的数组下标**（组由消费者决定，文件里不写） |
| tbl 有表头吗 | **没有**。唯一元信息是 entry 的 `dataSize`（u32 个数）和名字 |
| rtbl 在 PRES 里长什么样 | ds7 里的一条 **B 型**条目，指向 qpck 里的独立文件 |
| rtbl 文件里是什么 | N 个 **512 字节固定槽**，每槽一条路径引用；空槽整槽全零 |
| 槽里存的路径指向哪 | **任意位置**，实测 80% 根本不是本 PRES 的资源 |
| 为什么不用 tbl 代替 rtbl | tbl 只能指"同 PRES 内"，语音是跨 PRES 共享的 |
| 为什么不用 rtbl 代替 tbl | rtbl 每条约 512 字节，tbl 只要 4 字节；同包内的组合用 tbl 更省 |

## 5. 复现方式

```python
import struct

def u32(b, o): return struct.unpack_from("<I", b, o)[0]

def read_pres(path_in_qpck, ma):
    d = ma.read_path(path_in_qpck)
    cc = struct.unpack_from("<i", d, 0x1C)[0]
    a0 = 0x20 if cc <= 1 else u32(d, 0x20)
    for ds in range(8):
        hdr, cnt = struct.unpack_from("<II", d, a0 + ds * 8)
        for k in range(cnt):
            p = hdr + k * 32
            raw, size, nameat, namecnt = struct.unpack_from("<IIIi", d, p)
            typ, addr = raw >> 28, raw & 0x0FFFFFFF
            yield ds, k, typ, addr, size, nameat, namecnt

def read_tbl(d, addr, size_words):
    # size 单位是 u32 个数
    return struct.unpack_from("<%dI" % size_words, d, addr)

def read_rtbl_slot(rtbl_bytes, slot_index):
    blk = rtbl_bytes[slot_index * 0x200 : (slot_index + 1) * 0x200]
    if u32(blk, 0) == 0:
        return None                      # 空槽
    return bytes(blk[0x20:blk.find(b"\x00", 0x20)]).decode("utf-8", "replace")
```

> 本文两个实例均可用 §5 给出的代码自行复现（完整转储 / 字段级说明）。

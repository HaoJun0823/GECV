## 1. PRES 在整条链路中的位置

```
游戏目录
 └─ *.qpck                      归档容器：平铺的 (CRC64 哈希 → 数据块) 表，**不存文件名**
     └─ PRES                    资源树：登记"有哪些资源、叫什么、怎么取"
         └─ country             语言分组：1 或 6（EN/FR/IT/DE/ES/RU）
             └─ dataset         8 类角色：res / prx / asset / unk / conf / tbl / text / rtbl
                 └─ entry       条目：占位(0) / 虚拟引用(B) / 真实数据(F)
                     ├─ pool     本 country 内的内嵌数据与名字区
                     ├─ 尾部池   `pkgSize` 之后、跨 entry 复用的共享数据
                     └─ blz4     （可选）被压缩的资源在此解开
                         └─ tr2 / kst1 / gnf / is14 / ns3bank …  真正的叶子格式
```

**关键点**：qpck 只解出哈希名，PRES 才提供语义。二者通过

```
PRES 里的路径字符串 --CRC64--> qpck 的 TOC 哈希
```

绑定（见 [§10](#10-路径--qpck-哈希)）。

## 2. 文件整体布局

```
+0x0000  头部 32 字节
+0x0020  country 表            country_count × 8 字节            （country_count = 1 时**不存在**）
+0x0020  ┐                                                       （country_count = 1 时 body 直接从这里开始）
 或      │ country 体 #0        16 字节对齐，长度 = 表里登记值
+0x0050  ┘
         │ country 体 #1
         │ ...
         │ country 体 #(country_count-1)
+ pkgSize ┐
         │ 尾部共享池（被多个 entry 复用的数据块，16 对齐首尾相接）
+ EOF    ┘ 文件长度 = 尾部池总长向上 16 对齐
```

**硬约束（全部【实测】）**

| 约束 | 验证规模 |
|---|---|
| 文件总长是 16 的整数倍 | 8,586 / 8,586 |
| 每个 country 体起点 16 对齐 | 31,656 / 31,656 |
| `pkgSize = 0x20 + country_count×8 + Σ(country 体长度)`（cc ≥ 2 时） | 4,614 / 4,614 |
| `country_count = 1` 时无 country 表，body 起点恒为 `0x20` | 3,972 / 3,972 |
| `(文件长 - pkgSize)` 是 16 的整数倍 | 8,586 / 8,586 |

示例（GER 入口 PRES，`bin/resconv_pc/src/system/system.res`，908,640 字节）：

```
country_count = 6
country 体: 0x0050 / 0x8400 / 0x107B0 / 0x18B60 / 0x20F10 / 0x292C0   每个长 0x83B0
pkgSize    = 0x31670  (202,352)
尾部共享池 = 0x31670 .. 0xDDD60  (706,288 字节)
```

## 3. 头部（32 字节）

| 偏移 | 类型 | 字段 | PC 实测 | 说明 |
|---|---|---|---|---|
| `+0x00` | u32 | `magic` | `0x73657250` | 字节序列 `50 72 65 73` = `"Pres"` |
| `+0x04` | u32 | `groupOffset` | **恒 0** | 主机版是组表偏移；PC 弃用，8,586/8,586 全 0 |
| `+0x08` | u8 | `format` | **恒 8** | 8,586/8,586 全 8 |
| `+0x09` | u8 | `version` | **恒 3** | 【反汇编】引擎硬校验，非 3 直接报错退出 |
| `+0x0A` | u16 | `packageId` | 多数为 **0** | 见下方说明 |
| `+0x0C` | u32 | `sign` | **恒 1** | 仅低 2 位有效；高 30 位是 CeckSum 槽，PC 不计算、恒 0 |
| `+0x10` | u32 | `pkgSize` | 见 §2 | country 表 + 全部 country 体的总长（**不含**尾部池） |
| `+0x14` | u32 | `rdpDoff` | **恒 0** | 主机版：rdp 相关；PC 无 rdp |
| `+0x18` | u32 | `rdpSize` | **恒 0** | 同上 |
| `+0x1C` | i32 | `countryCount` | 1 或 6 | 见 §4 |

> ⚠️ **最容易踩的坑**：`+0x1C` 在主机版是 `decSize`（解压后大小），在 PC 版是 `countryCount`。
> 同一偏移、完全不同含义。**不要拿 PSV 的 `Pres.cs` 直接套 PC**（详见 §12）。
>
> `+0x08` 起的 4 字节整体读作一个 u32 是 `0x7C6E0308` = `format`(1) + `version`(1) + `packageId`(2)。
> 一手规格里把这三个当成 `magic_1/2/3`，其实是三个独立字段（见 §13）。

### 3.1 `packageId` 的实际分布【实测】

此前只看到入口 PRES 的 `0x7C6E`，误以为它是全局常量。全量统计后结论不同：

| 取值 | GER | GE2RB | 典型文件 |
|---|---|---|---|
| `0x0000` | 2,942 | 5,624 | 绝大多数子 PRES |
| `0x7C6E` | 1 | 1 | **入口 `system.res`** |
| `0x1DA3` / `0x28C0` / `0x04A3` / `0x3426` / `0x0663` / `0x73DD` … | 各 1 | 各 1 | `x005_at3.res`、`player_effect_*.res` 等 |

关键观察：

- 取值高度稀疏——8,586 个 PRES 里只有 **11 种取值**，且除 0 之外每种**最多 1 个文件**。
- **GER 与 GE2RB 的取值集合完全相同**（含那几个非 0 值），说明它是**打包工具生成的稳定标识**，
  而不是随作品变化的运行时参数。
- `sign` 则 8,586/8,586 恒为 1。

**推断（【推测】，未验证）**：`packageId` 可能是 resconv 打包时给"一次打包单元"分配的编号，
入口 PRES 固定拿到 `0x7C6E`。它对读取无影响（我们解析全部 8,586 个文件都不需要它）。

## 4. country 层（语言分组）

### 4.1 两种布局

`countryCount` 决定头部之后怎么走：

| 取值 | 布局 | 实测 |
|---|---|---|
| `1` | **没有 country 表**。country 体紧接头部，起点 `0x20`，长度 = `pkgSize - 0x20` | 3,972 个文件 |
| `6` | `0x20` 起是 6 条 8 字节表项，之后才是 6 个 country 体 | 4,614 个文件 |
| `12` | 【反汇编】引擎支持：表项索引 = `6 × global_A() + global_B()`，即两个维度的笛卡尔积；两个全局量的语义未定 | PC 数据**未见** |

> 引擎里不存在"其它取值"。`12` 的分支是把语言维度乘 6 后加上第二维，
> 用于同一语言的多套资源（对应主机版的多区域/多音轨形态）。
> PC 版发行版只发 1 和 6。

### 4.2 country 表

`+0x20` 起，`countryCount` 条，每条 8 字节：

| 偏移 | 类型 | 字段 |
|---|---|---|
| `+0x00` | u32 | 该 country 体在文件内的**绝对偏移** |
| `+0x04` | u32 | 该 country 体的**字节长度** |

### 4.3 country 顺序 = EN / FR / IT / DE / ES / RU

**【实测】** 对 GER 入口 PRES 逐 country 统计路径里的语言 token：

| country | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 出现的语言 token | `en` | `fr`（+`en`） | `it`（+`en`） | `de`（+`en`） | `es`（+`en`） | `ru`（+`en`） |

6 个 country 的 dataset 条目数、country 体长度**完全相同**（GER 各 208 条 / `0x83B0`），
差异只体现在 `data/Locale/exported/{lang}/...`、`.../ps4_{lang}/...` 这类路径字符串上。
这印证了 country 是**同一套资源结构 × 语言文本副本**的关系。

## 5. dataset 层（8 组目录槽）

### 5.1 目录槽

每个 country 体开头是 8 条目录槽，每条 8 字节，顺序**固定**：

| # | 名称 | 内容 | 数据位置 |
|---|---|---|---|
| 0 | `res` | 子 PRES | qpck（B） |
| 1 | `prx` | 外部模块声明 | qpck（B） |
| 2 | `asset` | **资源主体**：贴图 / 音频 / 布局 / 字体… | 尾部共享池（F）或 qpck（B） |
| 3 | `unk` | **恒空**（两作 0 条） | — |
| 4 | `conf` | 配置引用 | qpck（B） |
| 5 | `tbl` | 散表（u32 数组） | country body 内嵌（F） |
| 6 | `text` | 文本（按语言分开） | country body 内嵌（F） |
| 7 | `rtbl` | rdp/资源引用表 | qpck（B） |

槽结构：

| 偏移 | 类型 | 字段 |
|---|---|---|
| `+0x00` | u32 | 该 dataset 的 **entry 头数组**起点（绝对偏移） |
| `+0x04` | u32 | 条目数 |

### 5.2 两条硬不变量【实测】

1. **entry 头数组按 dataset 号升序、首尾相接连续排列**，起点恒为 `country + 0x40`。
   （105,688 / 105,688 个非空 dataset 通过）
2. **条目数为 0 的槽，offset 字段恒为 0**（不是"指向自己"）。

```
country 体起点 ─────────────────────────────────┐
  +0x00  8 × 8 目录槽                             │
  +0x40  entry 头数组：ds0 的全部 → ds1 的全部 → … │  每条 32 字节
         = country + 0x40 + 32 × Σ(count)
  pool：payload 与名字区交错（见 §7）
country 体终点 ────────────────────────────────┘
```

因为 entry 头是 32 字节、目录槽区是 64 字节，所以 **pool 起点天然 16 对齐**。

## 6. entry 层（条目头与名字区）

### 6.1 entry 头（32 字节）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `+0x00` | u32 | `typeAndAddress` | 高 4 位 = 类型，低 28 位 = 数据地址（**绝对文件偏移**） |
| `+0x04` | i32 | `dataSize` | 单位见 [§6.4](#64-datasize-的单位规则) |
| `+0x08` | i32 | `nameTableAt` | 名字指针数组的**绝对偏移** |
| `+0x0C` | i32 | `nameCount` | 名字项数（含属性槽） |
| `+0x10` | i32 | — | **实测恒 0** |
| `+0x14` | i32 | — | **实测恒 0** |
| `+0x18` | i32 | — | **实测恒 0** |
| `+0x1C` | u32 | `decompSize` | 解压后大小；语义见 [§6.5](#65-decompsize-的语义) |

地址打包（PRES 里最容易看错的一处）：

```c
uint32 raw   = read_u32(entry);
uint32 type  = raw >> 28;          // 高 4 位
uint32 addr  = raw & 0x0FFFFFFF;   // 低 28 位，绝对文件偏移
```

> `+0x10/+0x14/+0x18` 三个字段在一手规格里写作"1,2,3 未知，只会被游戏载入"。
> 实测 340 万条 entry **全部为 0**，应视为保留字段。

### 6.2 类型：PC 只有 0 / B / F

| 类型 | 十六进制 | 含义 | 数据位置 |
|---|---|---|---|
| `0` | `0x0` | **占位条目**：有名字、无载荷 | 无 |
| `B` | `0xB` | **虚拟引用**：`addr` 处是 NUL 结尾路径串 | 在 pool 里；实际文件在 qpck |
| `F` | `0xF` | **真实数据**：内嵌载荷 | pool 或尾部共享池 |

**【反汇编】引擎侧解释**：

- `0xB` → `*a2 = resBase + (raw & 0xFFFFFFF)`，并置标记位 `0x2000000`
  —— 把低 28 位当成**指向 res 载入缓冲内的指针**，即路径字符串地址。
- `0xC..0xF` → 同样的 `resBase + offset`，但置标记位 `0x4000000`
  —— 指向 res 缓冲内的**数据**。PC 只用 `0xF`。
- `0x3` / `0x4` / `0x5` / `0x6` 属于 rdp 体系（见 §11、§12），**PC 资产从不出现**。

> 这解释了 PC 与主机版的根本差异：**qpck 取代了 rdp 的角色**，
> 所以 PC 只需要"路径引用"和"内嵌数据"两种形态，不需要"数据在哪张 rdp 的第几块"。

### 6.3 名字区与名字槽语义

`nameTableAt` 处是 `nameCount` 个 u32 指针，每个指向一个 NUL 结尾的字符串：

```
nameTableAt → ┌ ptr[0] ┐
              │ ptr[1] │
              │  ...   │
              │ ptr[n] │
              └────────┘
              然后是字符串池：s0\0 s1\0 ... s(n-1)\0
```

| 槽 | 含义 | 说明 |
|---|---|---|
| `names[0]` | 基名 | 例 `god_menu` |
| `names[1]` | 扩展名 | 例 `res` / `gnf` / `tr2` / `rtbl` / `isuz`；**引擎靠它判定子 PRES** |
| `names[2]` | **恒空串** | 入口 PRES 918/918 为空 |
| `names[3]` | **完整资源路径** | 例 `data/GameData/.../X.gnf`；也是外部化/CRC64 的 key |
| `names[4..]` | **属性槽** | `KEY=VALUE` 或裸标志 |

还原文件名：`names[0] + ("." + names[1] if names[1] else "")`。
**【反汇编】** 子 res 判定就是 `strcmp(names[1], "res") == 0`。

## 7. body 与 pool 布局（核心）

这一节是本文档最关键的算法。按它重建，**3,403,114 条 entry 的地址零失败**。

### 7.1 每条 entry 的 chunk

pool 里每条 entry 占一个 chunk，由两段组成，各自 16 对齐：

```
chunk = align16(payload) + align16(names)
```

**payload 长度**

| 情况 | payload 原始长度 |
|---|---|
| 类型 `B` | `len(路径串) + 1`（含 `\0`） |
| 类型 `F` 且 `nameCount ≤ 3`（本地载荷） | `dataSize`（`tbl` 要 ×4） |
| 类型 `F` 且 `nameCount > 3`（**共享数据**） | **0**（数据在尾部池，见 §7.3） |
| 类型 `0` | **0**（但名字区照常写） |

**names 长度**

```
names_raw = nameCount × 4                        # 指针数组
          + Σ (len(names[i]) + 1)                # 字符串池
          + (是 _EXISTS= 条目 ? ceil(dataSize/4096) : 0)   # 位图，紧跟其字符串
names = align16(names_raw)
```

> **类型 `0` 的条目也占 pool 空间**：它没有 payload，但名字区（`nameCount` 个指针 + 字符串）
> 照常写在 pool 里。全库 149,792 条类型 0 条目都是这个形态，不能因为"没有数据"就跳过。

**两个地址字段**

```
nameTableAt = poolAt + payload_len_aligned     # 无名字区（chunk 为 0）时写 0
dataAt      = poolAt                           # 类型 B / 本地 F（payload 在 pool 里）
            = 尾部池中该 key 的偏移             # 共享 F（payload 在文件尾）
            = 0                                # 类型 0（无 payload）
```

> ⚠️ 共享 F 条目的 `dataAt` 指向**尾部池**，而 `nameTableAt` 仍指向**本 country 的 pool**。
> 两者不在同一区域，这是最容易写错的地方。

### 7.2 pool 的物理顺序：按 pair 的首次偏移排序（★）

pool 里**不是**按 dataset 0→7 顺序排列，而是：

```python
# 1) 每个 dataset（pair）算出"首次池偏移"
for ds in range(8):
    first[ds] = 0
    for e in entries[ds]:
        shared = (e.type == 0xF and e.nameCount > 3)
        off = e.nameTableAt if (shared or e.dataAt == 0) else e.dataAt
        if off > 0:
            first[ds] = off
            break                       # 取第一个 > 0 的

# 2) 非零的按偏移升序，零的排在最后
order = sorted(range(8), key=lambda ds: first[ds] or INF)

# 3) 逐个 dataset 逐条 entry 依次追加 chunk
poolAt = pool_start                     # = country + 0x40 + 32*Σcount，天然 16 对齐
for ds in order:
    for e in entries[ds]:
        ... 见 §7.1 ...
        poolAt += chunk
```

**为什么是这个顺序**：原始打包器在写 pool 时就是按"哪个 dataset 更早把数据放进池"来排的，
读回时只能靠 `first[]` 反推。这也是为什么 §5.2 里 entry 头数组可以按 ds 号连续排，
而 pool 却必须乱序——**头数组和 pool 是两个独立的排列维度**。

### 7.3 尾部共享池

`pkgSize` 之后是被多个 entry 复用的数据：

```
key = names[3]（完整资源路径）
```

打包规则【实测 8,523/8,523 精确】：

```python
# 1) 按 names[3] 去重，记录"首次出现的 dataAt"
seen = {}
for e in 所有 country 的所有 entry（按 country 顺序、ds 顺序、entry 顺序）:
    if e.type == 0xF and e.nameCount > 3:
        seen.setdefault(e.names[3], e)      # 只保留第一次

# 2) 按首次出现的偏移升序排列，各自 16 对齐后链式拼接
cursor = pkgSize
for key in sorted(seen, key=lambda k: seen[k].dataAt):
    assert align16(cursor) == seen[key].dataAt    # ← 实测全部成立
    cursor = seen[key].dataAt + seen[key].dataSize

# 3) 末尾再向上 16 对齐，即文件长度
assert align16(cursor) == file_size               # ← 实测全部成立
```

**要点**

- **不重复存放**：同一 `names[3]` 在多条 entry（甚至多个 country）中只写一份。
  这是"跨 country 共享内容池"的机制——6 国文件里 asset 的数据被 6 个 country 引用同一份。
- **偏移可乱**：因为是按"首次出现"排，所以同一个 dataset 内的偏移可能不连续。
- **无空隙**：除了 16 对齐填充，池内没有空洞。
- **8,523 个含尾部池的文件全部满足上述三条**；其余 63 个文件没有共享数据，`pkgSize == file_size`。

### 7.4 对齐规则汇总

| 对象 | 对齐 |
|---|---|
| 文件总长 | 16 |
| country 体起点 | 16 |
| entry 头数组起点 | 天然 16（`country + 0x40`） |
| pool 起点 | 天然 16（头数组长度是 32 的倍数） |
| 每个 chunk 的 payload 段 | 16 |
| 每个 chunk 的 names 段 | 16 |
| 尾部池每个数据块 | 16 |
| 尾部池总长 | 16 |

> 这说明 **下标是"数组位置"，不是"有效资源计数"**——重建时若删除 type 0 占位，
> 所有 `tbl` 的索引都会错位。**这是改包时最容易翻车的地方。**

### 8.7 `rtbl`（dataset 7）—— 引用表 + 占用位图

**角色**：指向一个 `*.rtbl` 文件（在 qpck 里），该文件按 **0x200 字节一槽**记录间接资源引用。

| 项 | GER | GE2RB |
|---|---|---|
| 条目数 | 2,532 | 2,082 |
| 类型 | 100% `B` | 100% `B` |
| `nameCount` | **恒 5** | 恒 5 |
| `names[3]` | `*.rtbl` 路径 | 同 |
| `names[4]` | **恒 `_EXISTS=`** + 紧跟位图 | 同 |
| `dataSize` | **= 目标 rtbl 文件字节数** | 同 |

**【实测】`dataSize` 就是目标文件长度**：4,614/4,614 条 rtbl 的 B 类型 `dataSize` 非 0
（全库唯一一种 `B` 类型带 size 的情况）；抽 769 条与 qpck 实际文件长度比对，全部相等。

#### `_EXISTS=` 位图的真实语义（本次新解出）

**位图长度** = `ceil(dataSize / 4096)` 字节，紧跟在 `_EXISTS=` 字符串（含 `\0`）之后。
**每一位代表 rtbl 文件中的一个 0x200 槽是否被占用**，位序 LSB first：

```
bit i == 1   ⇔   rtbl[i * 0x200] 起的第一个 u32 != 0
```

裁决实验（`god_menu.res` 的 8 个 voice rtbl，共 1,111~1,831 槽不等）：

| 假设 | 逐 bit 匹配 |
|---|---|
| **槽占用**（`rtbl[i*0x200] != 0`） | **8 / 8 精确** |
| 4KB 页非零 | 0 / 8 |

例：`god_menu_Voice_Generic_Kouta_tbl.rtbl` 568,832 B = 1,111 槽，
位图 139 B = 1,112 bit，45 个 bit 为 1，与"该槽首 dword ≠ 0"逐 bit 一致。

**【已定论】全量验证**：对**全部 4,614 条** `_EXISTS=` 条目（GER 2,532 + GE2RB 2,082）
逐 bit 重建比对：

| 结果 | 数量 |
|---|---|
| 精确吻合 | **4,614** |
| 不一致 | **0** |
| 跳过（目标缺失/维度不符） | **0** |

> 不要把它理解成"数据是否为零"的位图。rtbl 里的"空槽"是整槽全 0，
> 所以这条判据等价于"该槽是否有条目"。

#### 8.7.1 【已定论】rtbl 槽内布局（全量验证）

rtbl 文件按 **0x200 字节一槽**切分，每槽是一个**极简版的 PRES entry**：

| 槽内偏移 | 类型 | 字段 | 实测 |
|---|---|---|---|
| `+0x00` | u32 | `typeAndAddress` | **恒 `0xB0000020`**：类型 `B`、地址 `0x20` |
| `+0x04` | u32 | `dataSize` | **恒 0**（B 类型不使用） |
| `+0x08` | u32 | `nameTableAt` | 名字指针数组位置，实测 `0x60/0x70/0x80/0x90/0xA0` |
| `+0x0C` | u32 | `nameCount` | **恒 4** |
| `+0x10`–`+0x1F` | 16 B | 保留 | **恒 0** |
| `+0x20` | 字符串 | **路径** | NUL 结尾，例如 `data/GameData/.../cmn_0000_Kouta.is14` |
| `+0x08` 处 | u32×4 | 名字指针 | 指向 4 个字符串 |
| 之后 | 字符串池 | `names[0..3]` | `names[0]`=基名、`names[1]`=扩展名（`res`/`is14`）、`names[2..3]` |

解码算法：

```python
for off in range(0, len(rtbl), 0x200):
    raw = u32(rtbl, off)
    if raw == 0:                       # 空槽：整槽全 0
        continue
    assert raw >> 28 == 0xB            # 恒为引用型
    path   = cstr(rtbl, off + 0x20)    # ← 这就是 qpck 的查找键
    nameAt = off + u32(rtbl, off + 0x08)
    nNames = u32(rtbl, off + 0x0C)     # 恒 4
    names  = [cstr(rtbl, u32(rtbl, nameAt + j * 4)) for j in range(nNames)]
```

**全量验证（GER 422 + GE2RB 347 = 769 个 rtbl 文件，189,794 个非空槽，176,469 个空槽）**

| 断言 | 结果 |
|---|---|
| 非空槽的 `raw0 >> 28 == 0xB` | **189,794 / 189,794** |
| `+0x00` 低 28 位 == `0x20` | **189,794 / 189,794** |
| `+0x04 == 0` | **189,794 / 189,794** |
| `+0x0C == 4` | **189,794 / 189,794** |
| `+0x10..+0x1F` 全 0 | **189,794 / 189,794** |
| `+0x20` 处路径可解析 | **189,794 / 189,794** |
| `+0x08` 指向的 4 个名字指针可解析 | **189,794 / 189,794** |
| `names[0]` 是路径的基名 | **189,794 / 189,794** |
| `names[1]` 是路径的扩展名 | **189,794 / 189,794** |
| **槽内路径的 CRC64 命中 qpck TOC** | **189,794 / 189,794** |
| 空槽（`raw0 == 0`）整槽全 0 | **176,469 / 176,469** |

扩展名分布：`res` 188,303 / `is14` 1,491。也就是说 **rtbl 绝大多数指向子 PRES**，
少数指向音频。`names[1] == "res"` 时，该槽的值就是一个可递归解析的子 PRES。

> **重大含义**：rtbl 的槽路径 **100% 能命中 qpck**，且它就是查找键。
> 这比 PRES 里 `B` 条目的命中率（98.83%/97.69%）还高——因为 rtbl 只登记真实存在的资源。
> 所以 **rtbl 是补全名字表的第二把钥匙**（`topology.md` 提到的"42.9% 覆盖率提升"就来自这里）。

#### 8.7.2 与 PRES entry 的关系

rtbl 槽和 PRES entry 共用同一套字段布局（`typeAndAddress / dataSize / nameTableAt / nameCount`），
但**简化到极致**：地址固定 `0x20`、大小固定 0、名字固定 4 项。
可理解为「把一串 entry 头平铺成固定步长的数组，省掉 PRES 的目录层」。

只能靠魔数嗅探**：

```
0x34 0x7A 0x6C 0x62   →  "blz4"
```

| 判据 | 行为 |
|---|---|
| 载荷前 4 字节 == `blz4` | 解压；`decompSize` 即解压后长度 |

| | GER | GE2RB |
|---|---|---|
| `asset` F 条目总数 | 800,360 | 1,110,428 |
| 其中 blz4 | 731,320（91.4%） | 1,027,693（92.5%） |
| 其中明文 | 69,040 | 82,735 |

> **MD5 是硬校验**：blz4 头部 `+0x10` 存解压结果的 MD5。
> `gecv.blz4.decompress()` 默认校验，抽样 90 条（两作 country 0 全部 asset）全部通过。
> 分块与旋转写入算法见 `docs/res-压缩段说明.md`，本文不重复。

**注意**：`tbl` / `text` / `rtbl` 的载荷**一律明文**，从不压缩。

## 10. 路径 → qpck 哈希

qpck 的 TOC 只存 64 位哈希，路径归一化后算 CRC64（算法见 `qpck.md` §4）：

```
1. 反斜杠 → 正斜杠
2. 去掉前导斜杠
3. 转大写
```

### 10.1 PRES 里有两类路径字符串

| 来源 | 典型形态 | 用途 |
|---|---|---|
| 类型 `B` 的 `dataAt` 处字符串 | `data/GameData/.../X.gnf` | 运行时按它去 qpck 取文件 |
| `names[3]` | `bin/resconv_pc/data/GameData/.../X.gnf` | 同上，且带 `bin/resconv_pc` 前缀 |

**【实测】命中率（全量，按条）**

| 检查 | 命中 | 未命中 |
|---|---|---|
| `B` 条目的路径串在 qpck TOC 中 | 407,476 | 22,913 |
| `B` 条目的 `names[3]` 在 TOC 中 | 109,938 | 320,451 |
| 两者都命中 | 109,938 | — |

`F` 条目的 `names[3]` 是否在 TOC 中与正确性**无关**（数据就在 PRES 里），
实测 404,871 命中 / 1,505,917 未命中 / 912,145 无 `names[3]`。

### 10.1.1 【已定论】用 `RefPath`，不用 `names[3]`

这是本节此前唯一的"最高优先级未验证项"，现已用两条独立证据裁决：

**证据一（反汇编）** —— 运行时查找链：

| 地址 | 函数 | 行为 |
|---|---|---|
| `0x17E6756` | qpck 查找 | 复制 `a2` 路径 → 调用 `*(this+3)` 回调做归一化 → `sub_17EAB2F` 算 CRC64 → `sub_17E7E9E` 在 TOC 内二分查找 |
| `0x17EAB2F` | CRC64 | 查表实现，表地址 `dword_13F7830`/`dword_13F7834` |
| `0x17E7E9E` | 二分查找 | TOC 每条 20 字节，比较 `*(u64*)(entry+8)`，即 TOC 的 hash 字段 |
| `0x13F7830` | CRC64 表 | **逐项与多项式 `0x95AC9329AC4BC9B5` 的反射表比对：`tab[0]=0`、`tab[1]=0x7AD870C830358979` 全部吻合** |
| `0x1BB3ADA` | 归一化回调 | 经 `toupper` 变换（`sub_18D3110` 是 `std::transform` 到 `toupper`） |
| `0x1BB5201` | qpck 初始化 | `v6[3] = sub_1BB3ADA` 装填上述回调 |

**证据二（数据裁决，决定性）** —— 拿真实 qpck TOC 当答案，对 25,858 条唯一 `RefPath`
逐个套用 5 种归一化变体，看哪种能命中：

| 归一化变体 | GER 命中 | GE2RB 命中 |
|---|---|---|
| **转大写**（+ 反斜杠转换 + 去前导斜杠） | **8,535 / 8,636（98.83%）** | **16,825 / 17,222（97.69%）** |
| 仅转大写 | 8,535 | 16,825 |
| 丢首字符后转大写 | 0 | 0 |
| 转大写后丢末字符 | 0 | 0 |
| 原样不处理 | 0 | 0 |

结论明确：

- **哈希键是 `RefPath`**（即类型 `B` 的 `dataAt` 处路径串），`names[3]` **不参与查找**。
  旁证：297,538 条 `B` 条目的 `RefPath` 命中而 `names[3]` 未命中，且两者哈希**不相等**
  （仅 132,851 条相等，都是 `prx` / 短名这类无前缀路径）。
- **归一化 = 转大写 + 反斜杠转斜杠 + 去前导斜杠**，与 `gecv.crc64.normalize_path()` 现有实现一致。
- 大小写**不敏感**是硬结论（不转大写直接 0 命中）。

> ⚠️ 关于 `sub_1BB3ADA` 的反编译：该函数寄存器复用严重，Hex-Rays 把
> `sub_18D3110(&a1, v7, v5, v3, toupper)` 的实参顺序显示得可疑（看起来像"跳过首字符"）。
> 但数据裁决给出 0% 命中的反证，说明那是反编译失真，**以数据为准**。
> 这也是一条方法论教训：寄存器分配复杂的函数，反编译不能单独作为结论。

### 10.1.2 【已定论】22,913 条未命中路径的归因

按扩展名与前缀分类，未命中高度集中：

| 类别 | GER | GE2RB | 说明 |
|---|---|---|---|
| `prx`（全在 `ds1`，且无目录） | 5,337 | 9,509 | **`system.prx` / `tree.prx` 这类模块名** |
| `is14`（`data/GameData/.../sound/`） | 6 | 7,886 | 音频 |
| `nus3bank` | 44 | — | 音频 |
| `wmv` | — | 118 | 视频 |
| `dat` / `gmo` | 1 | 8 / 4 | 杂项 |

**结论**：未命中**并非** `ps4/`、`psvita/` 移植残留路径（此前怀疑不成立），
而是 **`prx` 模块声明 + 部分音频/视频资源**——这些资源本就不在 qpck 里，
而是以外部文件或流媒体形式存在。对 `prx` 而言，路径本身就是模块名而非 qpck 键。

> 注意 `EXCLUDE_RDP` 属性也可能导致"不在 qpck"，但它与上面的未命中集合**几乎不重叠**
> （GER 302 条 `EXCLUDE_RDP` 中 84 条 `RefPath` 仍能命中 qpck）。

### 10.2 名字表的完整导出流程

```
入口：bin/resconv_pc/src/system/system.res   (CRC64 = ABADA8CF0A5BB972)
      │
      ▼ 沿类型 B 的路径递归（去重！）
   解析每一棵 PRES → 收集「B 的路径串」+「names[3]」
      │
      ▼ 对每个字符串算 CRC64
   dict[hash] = path          ← 名字表
```

**递归是必需的**：只解入口那一层拿到的路径数远少于完整名字表；
必须递归全部子树才能覆盖全部资源（实测 GER 递归 2,952 棵 PRES，GE2RB 5,634 棵）。

### 10.3 【已定论】多归档优先级：按前缀匹配 + 固定顺序首命中

`qpck.md` §5 把归档叠加描述为"先入为主（最先出现者胜）"。**反汇编给出了更精确的机制**：

`sub_1BB3B8D`（对外的取文件入口）按固定顺序遍历 4 个归档描述符：

```c
for (desc in [bin_patch, bin, conf, data]) {      // 0x1BB5201 里按此序装载
    // 1) 先做"前缀匹配"：路径是否属于该归档负责的目录
    if (strncmp(path, desc.name, len) != 0) continue;

    // 2) 前缀匹配通过后，才在该归档的私有 map 里找
    qpck = sub_1BB44A9(...);                       // std::map<string, ptr> 红黑树
    if (qpck != end) {
        if (sub_17E6756(qpck, path, out))           // 归一化 + CRC64 + 二分查找
            return hit;                            // ← 首个命中即返回
    }
    // 3) 本归档未命中，继续下一个
}
```

关键点：

| 项 | 结论 |
|---|---|
| 选择依据 | **先按路径前缀把请求归类到某个归档**，再在该归档内查哈希 |
| 命中策略 | **固定顺序、首个命中即返回**（确实是"先入为主"，但作用域是"前缀匹配到的归档"） |
| 与 mod 的关系 | 把文件放进 `bin_patch.qpck` 且**路径前缀与 `bin` 一致**时，会先命中 patch——这就是 mod 覆盖能生效的原因 |

归档前缀常量（`src\app_mod\patch_ix.cpp`）：

| 归档 | 前缀 | 说明 |
|---|---|---|
| `bin_patch.qpck` | `/bi` | 注意是 `/bi` 而非 `/bin` |
| `bin.qpck` | `/bin` | |
| `conf.qpck` | `/conf` | |
| `data.qpck` | `/data` | |

> 这说明 `qpck.md` 的"先入为主"结论**方向正确，但过于简化**：
> 真正的门控是"前缀 → 归档"的映射，哈希只在已选中的归档内生效。
> 实践含义：**改 `data/` 下的资源时，放进 `bin_patch` 不一定生效**，

| 项 | PSV / PS4 | PC |
|---|---|---|
| 数据容器 | `package.rdp` / `data.rdp` / `patch.rdp`，块号 `<< 11` | **qpck**，CRC64(路径) 索引 |

| TOC entry | 32B（ps4 64B），`+0x1C` = `decSize` | 32B，`+0x1C` = `decompSize` |

| `local` 组位置 | 文件尾 | — （PC 无此概念） |
| `rtbl` | 独立 `.rtbl` + 槽 `0x80`/`0x200` | 同槽 `0x200`，**外加 `_EXISTS=` 位图** |

## 16. 读取与重建伪代码

### 16.1 读取一个 entry 的完整流程

```python
def read_pres(data: bytes):
    assert data[:4] == b"Pres"
    fmt, ver = data[8], data[9]
    assert ver == 3                      # 引擎硬要求
    sign   = u32(data, 0x0C) & 3
    pkg    = u32(data, 0x10)
    cc     = i32(data, 0x1C)

    # ---- country 列表
    if cc <= 1:
        countries = [(0x20, pkg - 0x20)]
    else:
        countries = [(u32(data, 0x20 + c*8), u32(data, 0x24 + c*8))
                     for c in range(cc)]

    for (at, ln) in countries:
        # ---- 8 个 dataset 目录槽
        dirs = [(u32(data, at + ds*8), u32(data, at + ds*8 + 4))
                for ds in range(8)]

        # ---- entry 头数组（连续，起点 at+0x40）
        entries = {}
        for ds, (hdr, cnt) in enumerate(dirs):
            entries[ds] = [parse_entry(data, hdr + k*32, ds)
                           for k in range(cnt)]

        # ---- 尾部池的 key → 偏移（先扫一遍所有 country 才能完整）
        #      见 §7.3
```

### 16.2 重建 pool（写入侧必读）

```python
def layout_country(entries_by_ds) -> dict:
    """返回每条 entry 的 (dataAt, nameTableAt)，与官方文件逐字节一致。"""
    # 1) dataset 顺序
    first = {}
    for ds, ents in entries_by_ds.items():
        first[ds] = 0
        for e in ents:
            shared = (e.type == 0xF and e.nameCount > 3)
            off = e.nameTableAt if (shared or e.dataAt == 0) else e.dataAt
            if off > 0:
                first[ds] = off
                break
    order = sorted(first, key=lambda d: first[d] if first[d] else INF)

    # 2) 逐 chunk 排布
    pool = country_start + 0x40 + 32 * sum(len(v) for v in entries_by_ds.values())
    out  = {}
    for ds in order:
        for e in entries_by_ds[ds]:
            payload = payload_len(e, ds)            # §7.1
            names   = names_len(e)                  # §7.1
            chunk   = al16(payload) + al16(names)
            out[id(e)] = (
                pool if chunk else 0,               # dataAt（本地 F / B）
                pool + al16(payload) if chunk else 0,  # nameTableAt
            )
            pool += chunk
    return out
```

### 16.3 整体重建顺序

```
1. 头部：magic / format=8 / version=3 / packageId / sign=1
2. country 表（cc > 1 时）：偏移待定，先预留 cc*8
3. 每个 country：
   a. 8 个目录槽（偏移待定，先预留 64）
   b. entry 头数组（按 ds 0..7 连续）
   c. pool（§16.2）
   d. 回填目录槽偏移与条目数
4. 回填 country 表偏移与长度
5. pkgSize = 最后一个 country 末尾
6. 尾部共享池（§7.3）：按 names[3] 去重、按首次 dataAt 升序、16 对齐链式
7. 回填所有共享 F 条目的 dataAt
8. 文件整体 16 对齐收尾
```

> **第 2 步与第 6 步有依赖**：`pkgSize` 决定尾部池起点，而尾部池的 `dataAt` 又写进 entry 头。
> 因此写入必须**两遍**：先按"不改动数据布局"排好 pool 与 country 长度，
> 定下 `pkgSize`，再算尾部池偏移并回填。

### 16.4 写入与打包

本仓库目前**只实现了读**，未实现写。以下是从参考实现的 `Pres.Serialize()` 与实测不变量
反推出的写入侧要求，供后续实现参考（**尚未用本仓库代码验证**）：

| 步骤 | 要求 | 依据 |
|---|---|---|
| 头部 `format` / `version` | 必须写 `8` / `3` | 引擎硬校验 version |
| 头部 `+0x04` / `+0x14` / `+0x18` | 写 `0` | 全量实测 |
| 头部 `+0x0C` | 写 `1`（只填低 2 位） | 全量实测；CeckSum 已废弃 |
| `+0x10 pkgSize` | 算到最后一个 country 末尾，**不含**尾部池 | §2 |
| country 表 | 仅 `cc = 6` 时写；每项 (偏移, 长度) | §4 |
| entry 头 `+0x10/14/18` | 必须写 `0` | 全量实测 |
| `tbl` 的 `dataSize` | 写 **u32 个数**，不是字节数 | §6.4 |
| `text` 的 `dataSize` | 写**含 `\0`** 的字节数 | §6.4 |
| `tbl`/`text`/`rtbl` 的 `decompSize` | 必须写 `0` | §6.5 |
| pool 顺序 | 严格按 §7.2 的 dataset 排序规则 | 31,656 个 country 体 |
| 尾部池去重 | 按 `names[3]` 去重，首次偏移升序 | 8,523 个文件 |
| 空 dataset 槽 | `offset = 0`，`count = 0` | 全量实测 |
| `_EXISTS=` 位图 | 重建 rtbl 后必须按新槽数重算 | §8.7 |
| 末尾 | 整个文件向上 16 对齐 | 8,586 / 8,586 |
